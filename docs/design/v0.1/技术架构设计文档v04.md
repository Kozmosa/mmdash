# 技术架构设计文档 v0.4

> 本文档是 `设计文档 v0.1` 的技术实现细化与扩展。原设计中的产品功能、交互、约束和首版范围全部保留；本文新增的模块化单体、BFF、OpenAPI、Job Queue、Outbox、Artifact、RBAC、Data Hub 和多 Runtime 设计用于支撑原功能，不得反向裁剪原设计。
> 

**首版技术组合**

```
Caddy
+ Next.js Web
+ TypeScript Web BFF
+ TypeScript MCP Gateway
+ Go 本地 CLI / stdio MCP
+ Go 模块化单体 Core
+ Python Worker
+ Go Box Gateway
+ PostgreSQL
+ MinIO / S3
```

**核心调用边界**

```
Browser → Web BFF → Core Server
Codex / Claude Code → clients/cli（stdio MCP）→ MCP Gateway → Core Server
Hermes API Server ↔ HermesAdapter；HermesAdapter → Hermes Dashboard 管理 API（仅 auto，可直连或经 Cloudflare Access）
Hermes → MCP Gateway → Project Data Hub
Core Jobs ↔ Python Worker
Core Box Control ↔ Box Gateway → Capability → Runtime
```

Web BFF、MCP Gateway、CLI、Worker 和 Box 均不得直接写业务数据库；权威业务状态由 Go Core Server 管理。

# 1. `apps/`

`apps/` 保存长期运行、可独立部署的 Web 与服务端接入应用。它们负责交互、认证、聚合和协议转换，不拥有核心领域状态。

## 1.1 `apps/web/`

技术：Next.js、React、TypeScript、Tailwind CSS、shadcn/ui、TanStack Query、Zustand、TipTap、Monaco Editor、ECharts。

一级导航保持原设计七项：

1. 首页；
2. mmdash Agent；
3. 进度跟踪；
4. 模型版本；
5. 论文写作；
6. 求解记录；
7. 设置。

Repo 和 Artifact 是独立功能模块，但不增加一级导航：Repo 的连接和分支配置进入设置页，代码树进入求解记录和引用组件；Artifact 通过首页、论文、模型和求解页面中的共享文件抽屉、附件库和选择器访问。

建议结构：

```
apps/web/src/
├── app/
│   ├── login/
│   ├── projects/
│   │   └── [projectId]/
│   │       ├── page.tsx
│   │       ├── agent/
│   │       ├── progress/
│   │       ├── models/
│   │       ├── article/
│   │       ├── experiments/
│   │       └── settings/
│   └── layout.tsx
├── features/
├── components/
├── hooks/
└── lib/
```

### 1.1.1 首页

必须展示：

- 题目卡片：标题、原始题目文件、关键约束；
- 当前阶段：Agent 判断结果，允许人工修正；
- 关键节点：最近截止时间和延期状态；
- TODO：今日、逾期、阻塞；
- 模型摘要：最新 Snapshot 和最近变化；
- 实验摘要：运行中、成功、失败和最新结果；
- 论文摘要：章节完成度、未审阅块、最近 Release；
- Agent 状态：Hermes 连接和最近进度评估时间。

每个摘要都必须可跳转到对应对象。数据由 Data Hub 聚合，不要求重复录入。

### 1.1.2 mmdash Agent 页面

必须支持：

- 创建、切换、重命名、结束、继续和分叉 Session；
- `main / progress / experiment` 三类持久化 Session；人类工作台仅创建/列出 `main`，后两类分别由 Progress 与 Experiment 内部流程拥有；
- 默认 Session；
- 消息历史、流式回复、工具调用、Run 状态；
- 停止、重新生成、重新执行；
- Hermes 运行时连接状态、`manual / auto` 管理模式和 MCP 配置状态；
- `manual` 模式下已配置 Dashboard 地址时显示 MCP 配置入口；
- `auto` 模式下显示管理地址可达性、认证链路和最近自动管理结果；
- 项目专用提示词自动生成、手工修改、恢复默认；
- 自动进度跟踪开关；
- Cron、事件触发任务、最近执行结果；
- 手动“重新评估进度”。

Hermes 保存完整消息历史；mmdash 保存 Session 索引、项目映射、名称、类型和状态。

### 1.1.3 进度跟踪页面

- 人工关键时间节点；
- TODO、负责人、来源、关联对象、时间和依赖；
- 看板：待办、进行中、阻塞、完成；
- 列表；
- 日历/甘特；
- 今日视图；
- 提醒和外部通知；
- Proposal 审阅。

关键节点未经人工确认不得由 Agent 修改。普通 TODO 默认允许 Agent 调整，也可在项目设置中切换为仅 Proposal。

### 1.1.4 模型版本页面

- 左侧版本时间线；
- 中间版本渲染；
- 右侧元数据、标签和说明；
- 两版本 Diff；
- 手动同步；
- 可选定时同步；
- Hash 不变时不创建 Snapshot；
- 不在 mmdash 中重做复杂模型编辑器。

### 1.1.5 论文写作页面

布局：左侧参考区，右侧块级 Markdown 编辑器，右上角显示 LaTeX 状态、Build 历史和 Markdown Commit 历史。

块级编辑器必须支持：

- 标题、段落、图片、表格、公式独立成块；
- 稳定 `block_id`；
- 拖拽排序和组合；
- `/` 命令；
- AI 修改以 Patch 呈现；
- 接受或拒绝 Patch；
- 行/块 Tag 和章节 Tag；
- Git 状态式颜色。

Tag：

```
章节tag：未编辑 / 未审阅 / 已审阅
块tag：AI 初稿 / 人工初稿 / AI 修订 / 人工修订 / 已审阅
```

附件进入注册表，至少保存：

```
attachment_id
filename
sha256
mime_type
description
source
created_at
recommended_usage[]
status
```

Markdown Commit 时可选择生成 LaTeX，也可对历史 Commit 单独 Build。同一 Commit 可以多次 Build；Release 绑定任意 Commit 的一次成功 Build。

### 1.1.6 求解记录页面

实验列表显示 Exp ID、名称、状态、创建者、时间和 source commit。

详情必须包含：

- 参数、环境、日志、失败原因、资源消耗和结果摘要；
- 代码快照或结果包文件树；
- 文本、图片、表格、JSON、CSV 和日志预览；
- AI/人工结果分析；
- 多实验比较；
- 有限文本编辑；
- 外部编辑器入口；
- 项目绑定且活跃的 Box。

点击 Box 可查看在线状态、负载、Gateway 版本、Capability、Runtime 和资源限制，并跳转设置页绑定、解除或更换 Box。

### 1.1.7 设置页

模块通过插槽注册设置：

- Project：题目、约束、成员和角色；
- Repo：Provider、仓库、三个分支和 Webhook；
- Artifact：不注册 Project 设置；对象存储和上传限制由系统部署环境变量管理；
- Agent：Hermes 和自动进度跟踪；
- Progress：通知渠道；
- Model：Notion；
- Article：Zotero、LaTeX 模板和论文规范；
- Experiment：Box、Runtime、资源和超时；
- MCP/API：用户 API Token 管理。CLI 的当前项目属于用户设备本地配置，不在 Web 设置页维护。

## 1.2 `apps/web-bff/`

技术：TypeScript、Node.js、Fastify、Zod、Pino、OpenAPI 生成的 Core Client。

职责：

- 浏览器认证；
- 当前用户和项目上下文；
- 页面级 API；
- Core API 聚合；
- 页面 DTO 转换；
- 错误转换；
- SSE、WebSocket 和文件流代理；
- 隐藏 Core 内部模块结构。

BFF 不直接访问 PostgreSQL、MinIO、Git、Hermes 或 Box，不生成 Exp ID，不实现领域状态机。

## 1.3 `apps/mcp-gateway/`

使用 TypeScript 和官方 MCP SDK，以 Streamable HTTP 向 CLI、Hermes 和外部 Agent 暴露受控能力。

首版 Tool：

```
project.list
project.get
data.list
data.read
experiment.create
experiment.run
experiment.status
result.get
context.promote
progress.recalculate
```

职责：

- MCP Session；
- 用户委托的 CLI 身份，以及 Agent 阶段引入的项目受限 Agent Token；
- Tool 注册、参数校验和权限；
- 项目解析；
- Core API 转发；
- MCP 错误转换；
- 审计。

MCP Gateway 不直接读取 Git、对象存储或业务数据库。

本地 Coding Agent 与独立 Agent Runtime 使用不同链路：Codex、Claude Code 等本地进程通过 Go CLI 的 stdio Bridge 接入；Hermes 等已绑定 Agent 实例使用自身 Agent Token 直接连接远程 Gateway，不经过 CLI。基座环境变量中的静态 CLI/Agent Token 只用于开发和边界测试，不能替代 Agent 阶段由 Core Auth 签发、哈希存储、可轮换和可撤销的产品凭证。

产品级 Agent Token 与用户 Session/API Token 使用同一个一级认证模型：Gateway 将客户端提供的原始 Token 传给 Core，不签发、不替换、也不附加第二枚 Gateway 访问 Token。差异只在授权范围：Agent Token 固定绑定单个 Agent 实例、Project 和精确 Tool 集；Gateway 先检查该 Tool 集，Core 再以同一 Agent 身份执行最终 Project/领域 RBAC 与 Audit。Core 只存在于部署私网，不发布生产宿主机端口且不由 Caddy 直连；Caddy 的用户/CLI `/v1` 流量进入 Web BFF，BFF 只允许用户 Session、用户 API Token 和明确的公开签名端点，拒绝 Agent 与服务凭证。

# 2. `clients/`

`clients/` 保存安装在用户设备上的客户端。它与 `apps/` 分离，因为 CLI 不是长期运行的服务，也不是服务端部署单元。

## 2.1 `clients/cli/`

CLI 是 Codex、Claude Code 等本地 Coding Agent 连接 mmdash 的入口，同时提供人工命令行操作。

CLI 使用独立 Go module 和单一原生二进制。建议结构：

```
clients/cli/
├── go.mod
├── go.sum
├── cmd/mmdash/main.go
└── internal/
    ├── app/
    ├── auth/
    ├── config/
    ├── credentials/
    ├── doctor/
    ├── extension/
    ├── mcpbridge/
    ├── output/
    └── features/
        ├── core/
        └── project/
```

首版命令：

```
mmdash login
mmdash logout
mmdash whoami
mmdash project list
mmdash project use <project_id>
mmdash project current
mmdash mcp
mmdash doctor
```

`mmdash mcp` 启动本地 stdio MCP Server，将请求通过 HTTPS / MCP Streamable HTTP 转发给 `apps/mcp-gateway/`。

调用链：

```
Codex / Claude Code
        ↓ stdio MCP
clients/cli
        ↓ HTTPS / MCP Streamable HTTP
apps/mcp-gateway
        ↓ Core OpenAPI
backend/cmd/core-server
```

CLI 负责：

- 登录和 Token 刷新；
- 系统安全凭证存储；
- 显式选择并保存当前项目；
- stdio 与远程 MCP 的桥接；
- 网络、认证和项目歧义诊断；
- 项目不明确时拒绝执行写操作。

CLI 不保存权威项目数据，不直接访问数据库、Git Provider、MinIO 或 Box。

CLI 的扩展采用编译期 Feature 注册，不使用 Go runtime plugin。Stage 3 只提供命令注册、配置、凭证、输出、诊断、HTTP/MCP Transport 和本地 Agent Bridge；Repo、Artifact、Progress、Model、Experiment、Article 等人工命令由所属阶段注册。MCP Bridge 应尽量透明转发 Gateway 的能力发现和 Tool 调用，因此服务端新增 Tool 原则上不要求发布新版 CLI。

# 3. `packages/`

`packages/` 保存 TypeScript 应用和客户端共享的库，不承载独立部署和业务所有权。

## 3.1 `packages/core-client/`

由 OpenAPI 生成的 Core Client，供 Web BFF、MCP Gateway 和必要的内部工具使用。

## 3.2 `packages/api-types/`

共享 API DTO、分页、错误、ID 和时间类型。只允许引用生成或稳定公共类型，不复制领域实现。

## 3.3 `packages/auth/`

浏览器和 TypeScript 服务间 Token 的通用处理；不拥有用户和权限数据。Go CLI 使用自身 module 内的认证客户端，并与相同服务端契约保持兼容。

## 3.4 `packages/validation/`

Zod/JSON Schema 公共校验、错误格式化和输入标准化。

## 3.5 `packages/errors/`

跨 TypeScript 应用共享错误码、用户消息和可重试标志。

## 3.6 `packages/logging/`

Pino 配置、字段约定、脱敏和 request_id 传播。

## 3.7 `packages/mcp-client/`

TypeScript 服务端接入和测试工具共享的 MCP Streamable HTTP Client。Go CLI 在自身 module 中实现 stdio Bridge 和远程 MCP Client；Hermes 是独立外部客户端，不复用 monorepo 内的 TypeScript 包。

## 3.8 `packages/ui/`

Web 通用 UI 组件，包括文件树、日志、Diff、时间线、Markdown、表格和状态展示。

# 4. `contracts/`

# 5. `backend/`

`backend/` 是 Go 模块化单体和权威业务数据的所在地。模块之间通过应用服务、只读查询接口和领域事件协作，禁止直接写其他模块表。

## 5.1 `backend/cmd/core-server/`

- 配置加载；
- HTTP Server；
- 模块注册；
- PostgreSQL、MinIO、Job Queue 初始化；
- 健康检查；
- 优雅退出；
- OpenAPI 暴露。

## 5.2 `backend/internal/auth/`

拥有用户、登录、Session/JWT、API Token、Agent Token、Box Token、撤销和身份上下文。

首版角色：

```
owner maintainer editor viewer agent box
```

## 5.3 `backend/internal/project/`

拥有项目、成员、角色、归档、题目结构化信息和关键约束。

```
problem_title
problem_summary
project_constraints[]
source_artifact_ids[]
```

原始题目文件由 Artifact 管理，Project 只保存引用。

## 5.4 `backend/internal/settings/`

拥有系统级和项目级配置、密钥加密、脱敏、模块设置注册和连接测试规范。具体 Git、Hermes、Notion、Zotero、通知、Box 配置由所属模块定义。

## 5.5 `backend/internal/repo/`

Repo 是独立功能模块和所有 Git 操作的唯一入口。

首版：

- 一个项目默认一个 Git Repo；
- `code / article / result` 三个逻辑工作区，映射到三个不同且已存在的远程分支；
- 已有 `main`、`master` 或其他分支可映射为逻辑 `code`；
- 首版不自动创建、重命名、删除或强制覆盖远程分支；
- Worktree 并行访问；
- Provider、状态、分支、Commit、文件树和文件内容；
- Webhook；
- 临时 Checkout；
- Core 内部受控文本写入、Commit 和普通 Push；Stage 1 Web 完全只读；
- article/result 提交；
- `ArticleWorkspace` 抽象，允许未来独立 article repo。

发布 `repo.commit.created/detected`，供 Agent、Model、Experiment、Article 和 Data Hub 消费。

仓库同步和 Git 子进程由 Go Core 内的 Repo Runtime 管理，不新增 Python Repo
Worker。文件树只在求解记录页出现；设置页只管理连接、分支映射、同步状态和
Webhook。

## 5.6 `backend/internal/artifact/`

Artifact 是独立模块，统一管理题目文件、普通附件、预览、构建产物和实验结果包。

拥有：

- 元数据、Hash、MIME、大小、来源和状态；
- Signed URL；
- Local、MinIO、S3 Adapter；
- 附件注册表；
- 预览索引；
- 来源对象关联；
- 小型 Git Artifact 与大型对象存储 Pointer。

Artifact 使用稳定逻辑 ID 和不可变 Version。固定系统 `kind`、固定系统 `source`
与用户自由 `tags[]` 分离；对象内容只在同一 Project 内按 SHA-256 与大小去重。
成功版本永久保留，普通删除只进入可恢复回收站；只有用户明确永久删除且 blob
无其他引用时才删除对象字节。

Stage 2 直接采用统一 multipart BlobStore 契约。MinIO/S3 通过短期预签名 part PUT
直传；Local 通过短期签名的 BFF/Core 流式路由传输。Core 负责动态 part size、
按需签名、List/Complete/Abort、过期会话清理和完成后的完整大小与 SHA-256
验证。对象存储 endpoint、public endpoint、bucket、凭据、上传限制、part size
和 TTL 全部来自系统环境变量，不属于 Project Settings。

Stage 2 Worker 只生成预览、缩略图和结构摘要，并保留
`SemanticDescriptionGenerator` 接口。LLM/多模态语义描述和自动
`recommended_usage` 延后到 Article；CLI 登录和项目选择由 Stage 3 的 Go CLI
基座实现，Artifact 人工命令由 Artifact 后续迭代通过 CLI Feature 注册机制补充。

## 5.7 `backend/internal/progress/`

拥有 Milestone、Task、Dependency、Reminder 和 Proposal。

规则：

- 关键节点由人创建，Agent 只能提出 Proposal；
- 普通 TODO 可配置为 Agent 自动调整或仅 Proposal；
- 提醒发布稳定领域事件，由 Notification 通过 NotificationAdapter 发送；
- 看板、列表、甘特和今日视图读取同一权威数据。

## 5.8 `backend/internal/notification/`

Notification 是内部收件箱和 Project 级外部通知的统一底座。它消费各领域模块发布的稳定事件，将通知事实、收件关系、站内状态和外部投递状态持久化，但不拥有邀请、任务、实验等来源业务对象的权威状态。

### 5.8.1 职责和非职责

Notification 拥有：

- Notification Type、模板、Recipient Resolver 和生命周期映射注册表；
- Notification、Recipient、Inbox Item、Project NotificationRule；
- External Delivery、Delivery Attempt、领取租约、重试和失败诊断；
- NotificationAdapter 注册、连接测试、内容渲染和安全错误转换；
- Inbox 查询、未读数、阅读与归档状态；
- Project 外部通知路由、配置状态读取和显式重新投递。

Notification 不拥有：

- Project 邀请、成员、角色、Progress Reminder、Task、Experiment 或 Article 的业务状态；
- Auth 用户邮箱变更和用户身份本身；
- Settings 密文、加密算法和 Secret 生命周期；
- Python Worker Job 或外部 Provider 的权威状态；
- 任意消息广播接口、任意 HTML 模板或由调用方指定的任意用户列表。

模块通过 Project/Auth 的只读接口解析当前用户和 Project 关系，通过来源模块命令执行通知 Action。除调用公开应用服务外，禁止查询或写入其他模块表。

Inbox 面向“需要某个用户注意或处理的消息”，不替代 Data Hub Activity Timeline；同一领域事件可以分别形成项目活动投影和个人 Inbox，但两者拥有独立查询、权限和留存语义。

### 5.8.2 包内结构

```text
backend/internal/notification/
├── module.go                 # HTTP、Event Consumer、Settings Type 和后台 Processor 注册
├── notification.go           # Notification、Recipient、Inbox Item 领域类型
├── registry.go               # Notification Type 与 Adapter Registry
├── template.go               # 字段白名单、模板版本和多渠道渲染
├── recipient.go              # 用户、邮箱、负责人、角色等收件人解析
├── inbox.go                  # Inbox 查询、未读、已读、归档
├── rule.go                   # Project NotificationRule
├── event_consumer.go         # Outbox/Event Bus 投影入口
├── delivery.go               # Delivery 状态机和重投用例
├── processor.go              # Delivery 领取、租约、超时、退避和限流

├── adapters/
```

可在实现时按测试和复杂度拆分文件，但 Type Registry、Inbox、Routing、Delivery Processor 和 Adapter 边界不得合并成直接发送 Webhook 的单一 Service。

### 5.8.3 Notification Type Registry

每个 Type Descriptor 包含：

```text
type_key
schema_version
source_event_types[]
accepted_event_schema_versions[]
scope = system | project
recipient_resolver
inbox_policy = required | default_on | optional | disabled
external_allowed
priority
template_key
template_version
allowed_template_fields[]
action_builder?
lifecycle_mappings[]
```

- Type Key 是稳定的小写点分名称，例如 `project.invitation.received`，版本由 Descriptor 和模板版本表达，不在运行时覆盖旧语义；
- Source Event 只提供结构化事实，Template Renderer 只读取 `allowed_template_fields`；
- Recipient Resolver 返回规范化目标，不接受事件提供的任意 Recipient ID 列表；
- `required` Inbox 类型不可被 Project Rule 关闭；
- External Renderer 可以减少字段，不能比 Inbox Renderer 暴露更多未经声明的数据；
- 重复 Type Key、重复来源映射、未知 Scope、无 Renderer、无 Resolver、空字段白名单或不兼容 Schema Version 在启动时失败；
- 首版注册显式 Type，不使用 `project.*`、`progress.*` 等通配符自动生成用户可见通知。

- Delivery 诊断：`(project_id, created_at DESC, delivery_id DESC)`。

### 5.8.5 状态机

Inbox 阅读状态：

```text
unread ↔ read
任一阅读状态 ↔ archived_at 有值
```

业务结果状态只允许单调变化：

```text
active → resolved | revoked | expired
```

终态不能被较早或重放的事件恢复为 active。事件乱序时使用 `occurred_at`、来源事件 ID 和终态优先级进行幂等判断。

Delivery：

```text
pending → sending → delivered
                  → retrying → sending
                  → failed
pending/retrying → cancelled
```

- Claim 在事务中执行 `FOR UPDATE SKIP LOCKED`，写入 `locked_by` 和 `lease_expires_at`；
- Lease 过期的 sending Delivery 返回 retrying，超过 `max_attempts` 转 failed；
- delivered、failed 和 cancelled 是当前 Delivery Key 的终态；
- 显式重投创建新 Delivery Key，不把 failed 原地改回 pending。

### 5.8.6 事件消费与邀请映射

首批 Event Consumer 名称固定为 `notification.inbox-project-invitations` 和 `notification.bind-registered-user`。

| 来源事件                         | Notification 行为 |
| -------------------------------- | ----------------- |
| `project.member.invited`         | 创建 `project.invitation.received`、邮箱/用户 Recipient 和 Inbox Item |
| `user.registered`                | 按规范化邮箱认领 pending Recipient，合并重复用户收件项 |
| `project.member.joined`          | 当载荷含 `invitation_id` 时将对应 Inbox outcome 更新为 resolved |
| `project.invitation.revoked`     | 将对应 Inbox outcome 更新为 revoked，取消尚未发送的关联 Delivery |
| `project.invitation.expired`     | 将对应 Inbox outcome 更新为 expired，取消尚未发送的关联 Delivery |

`project.member.invited` Schema 必须包含：

```text
invitation_id
project_id
normalized_email
role
invited_by_user_id
expires_at
```

不得包含邀请明文 Token。`project.member.joined` 在由邀请产生时必须包含 `invitation_id`，无邀请的直接成员写入可省略。

Event Handler 使用自己的 PostgreSQL 事务完成 Notification、Recipient、Inbox Item、Rule Snapshot 和 Delivery Upsert。Outbox Delivery 完成与 Handler 事务不是原子提交，因此所有写入都必须以来源事件 ID 幂等。

### 5.8.7 邀请 Action

Inbox Action 保存：

```text
action_type = project.invitation.accept
action_resource_id = invitation_id
```

它不保存 Token，也不直接修改 `project_invitations`。Project 提供：

```http
POST /v1/projects/invitations/{invitationId}/accept
```

该接口要求人类 Session/API Token，加载邀请后比较登录用户规范化邮箱，再检查未撤销、未过期、未接受和 Project 状态。成功后由 Project 原事务写成员关系和带 `invitation_id` 的 `project.member.joined`。

现有 Token Preview、Token Accept 和 Register-and-Accept 继续服务未登录用户。Notification 只在 `user.registered` 后认领 Inbox，不尝试从哈希恢复 Token。

### 5.8.8 Project Channel 与 Settings

Notification 注册两个 Project Scope Setting Type：

`notification.feishu_webhook`：

```text
enabled boolean
webhook_url secret
```

`notification.generic_webhook`：

```text
enabled boolean
endpoint url
signing_secret secret
```

- 通用 Endpoint 禁止 User Info 和内嵌凭据，只允许 HTTP/HTTPS；生产默认要求 HTTPS；
- 现有 Settings 唯一键是 `(scope_type, scope_id, type_key)`，因此首版每个 Project、每种 Adapter 最多一个渠道实例；
- Rule 的 `channel_keys` 只能引用上述已注册且启用的 Type Key；
- Settings 更新事件不包含值；Notification 在生成或领取 Delivery 时通过可信进程内 Resolver 获取当前配置；
- Delivery 保存 Channel Key 和 Rule Version，不保存解密配置；
- 删除设置后 pending/retrying Delivery 转 cancelled；发送中的请求允许结束，但不得继续重试；
- 多同类渠道需求必须通过未来显式的 Channel Collection 设计扩展，禁止生成动态 Setting Type Key 绕过注册表。

### 5.8.9 NotificationAdapter

Adapter 契约至少提供：

```text
Key() string
ValidateConfig(config) error
Test(ctx, config) ConnectionTestResult
Render(ctx, notification, templateVersion) RenderedMessage
Send(ctx, config, deliveryID, renderedMessage) SendResult
Classify(error/response) retryable + safeError
```

- Adapter 不读取数据库，不自行决定收件人或 Rule；
- `Send` 必须服从 Context Timeout，不在内存长期缓存明文 Secret；
- 飞书 Adapter 输出固定安全卡片/文本结构，不允许模板注入任意 JSON；
- 通用 Webhook 使用稳定 Envelope，并设置 `X-Mmdash-Delivery-Id`、`X-Mmdash-Notification-Type`、`X-Mmdash-Timestamp` 和 `X-Mmdash-Signature`；
- 签名以原始请求体和时间戳计算 HMAC-SHA256；连接测试使用独立测试载荷，不伪造业务 Notification；
- Adapter 返回 Provider Message ID（若有）、安全响应摘要和可重试分类，不把原始错误直接交给 API、日志或 Audit。

### 5.8.10 Delivery Processor

Delivery Processor 与 Outbox Processor 一样由 `core-server` 启动和优雅停止，但使用 Notification 自己的表和 Store：

```text
Event Consumer transaction
  → Notification / Recipient / Inbox Item
  → Rule evaluation
  → pending Delivery

Delivery Processor
  → claim with lease
  → resolve encrypted Setting in-process
  → render through Adapter
  → external HTTP call
  → append Attempt
  → delivered | retrying | failed
```

- Processor 支持多 Core 实例，不使用进程内队列作为权威状态；
- Retry 默认指数退避加抖动，并尊重 Provider `Retry-After`；
- 网络错误、429 和可恢复 5xx 可重试；配置缺失、认证失败、签名错误和不可恢复 4xx 终止；
- 网络超时可能发生“Provider 已接收但响应丢失”，因此外部语义为至少一次；
- 普通 Outbox Replay 命中相同唯一键，不新增已存在 Live Delivery；管理员重投生成新 `delivery_key` 和 Audit；
- 首版不使用 Python Worker Job Queue，避免把渠道 Secret 发送给 Worker，也避免 NotificationAdapter 在 Go/Python 各实现一套。

### 5.8.11 HTTP API

Inbox：

| Method | Path                              | 语义 |
| ------ | --------------------------------- | ---- |
| GET    | `/v1/inbox`                       | 当前用户 Cursor 分页，支持 Project、Type、阅读、归档和 Outcome 筛选 |
| GET    | `/v1/inbox/unread-count`          | 当前用户全局或指定 Project 未读数 |
| GET    | `/v1/inbox/{inboxItemId}`         | 当前用户收件项详情 |
| PATCH  | `/v1/inbox/{inboxItemId}`         | 修改 `read_state`、归档或取消归档 |
| POST   | `/v1/inbox/mark-all-read`         | 按可选 Project/Type 范围批量已读 |

Project Notification：

| Method    | Path                                                                                | 语义 |
| --------- | ----------------------------------------------------------------------------------- | ---- |
| GET/PATCH | `/v1/projects/{projectId}/notification-channels/{channelKey}`                       | 脱敏读取、启停和更新渠道 |
| POST      | `/v1/projects/{projectId}/notification-channels/{channelKey}/test`                  | 使用保存配置执行安全连接测试 |
| GET/PUT   | `/v1/projects/{projectId}/notification-rules/{typeKey}`                             | 读取或版本化更新 Rule |
| GET       | `/v1/projects/{projectId}/notification-deliveries`                                 | Cursor 分页查询投递与安全诊断 |
| POST      | `/v1/projects/{projectId}/notification-deliveries/{deliveryId}/retry`               | 带原因显式重投 |

- Inbox Item ID 对其他用户始终返回 404，避免确认消息存在；
- PATCH 不能修改 outcome、Notification 内容、Recipient 或动作；
- Rule PUT 携带 `version`，冲突返回 409；
- Channel API 是 Notification 面向浏览器的组合契约，内部调用 Settings Service，不直接写 `settings_values`；
- BFF 在 `/api` 下镜像这些契约，仅处理 Session Cookie、CSRF 和浏览器安全错误，不缓存权威未读数。

### 5.8.12 权限

| 操作                         | 权限 |
| ---------------------------- | ---- |
| 读取/修改个人 Inbox          | 收件用户本人 |
| 查看脱敏 Channel 状态        | Project 成员 |
| 更新/测试/删除 Channel       | owner、maintainer |
| 查看和更新 Rule              | owner、maintainer |
| 查看 Delivery 诊断           | owner、maintainer |
| 显式重新投递                 | owner、maintainer，并写 Audit |
| 产生领域通知                 | 已注册 Event Consumer 或 Core 内类型化用例 |
| Agent/Box 读取人类 Inbox     | 禁止 |
| Agent/Box 管理外部渠道       | 禁止 |

用户已经被移出 Project 后仍可读取此前明确投递给自己的 Inbox Item，但 Action 必须由来源模块按当前权限拒绝；Project Delivery 和 Channel 管理则立即失去访问权。

### 5.8.13 安全、留存和可观测性

- 邀请 Token、Session、API Token、Webhook Secret、带凭据 URL、Signed URL 和完整 Provider 响应不得进入 Notification、Outbox、Attempt、Audit 或日志；
- Inbox 文本按纯文本或受控富文本 AST 渲染，禁止保存和渲染任意 HTML；
- 默认不允许外部模板包含邮箱和个人资料；Type Descriptor 必须显式声明可外发字段；
- Inbox 首版不硬删除，归档只影响默认列表；后续由 Core 内维护任务按统一 Retention Policy 清理超过期限的 resolved/expired 项；
- Delivery Attempt 的响应摘要限制长度并脱敏，失败记录保留稳定错误码；
- Metrics 至少包括 `notification_created_total`、`notification_inbox_unread`、`notification_delivery_pending`、`notification_delivery_duration`、`notification_delivery_retries_total`、`notification_delivery_failures_total`；
- 日志携带 `notification_id / delivery_id / project_id / source_event_id / request_id`，不记录模板数据全文；
- Readiness 不因单个外部 Provider 故障失败，但 Delivery 积压、终态失败和租约恢复必须可观测。

### 5.8.14 跨模块接入规则

新模块接入 Notification 时必须同时提交：

1. 稳定领域事件及 JSON Schema；
2. Notification Type Descriptor 和模板；
3. Recipient Resolver 与权限说明；
4. Inbox/External 策略和字段白名单；
5. Action 对应的来源模块命令（若有）；
6. 创建、重复消费、生命周期终态、脱敏和 E2E 测试。

禁止新模块直接依赖飞书、Webhook 或 Notification 数据表。Progress Reminder 改为发布稳定事件，由 Notification 决定 Inbox 和外部路由；其他模块遵循同一规则。

## 5.9 `backend/internal/datahub/`

Data Hub 是跨模块统一读取和项目上下文层，不替代各模块的权威数据。

拥有：

- Stable Object ID；
- Object Registry；
- Activity Timeline；
- Project Context；
- Context Proposal；
- `data.list` 和 `data.read` 路由；
- 首页聚合投影。

各模块通过事件更新投影，并实现完整对象读取 Adapter。

## 5.10 `backend/internal/agent/`

`AgentAdapter` 是 Agent 域定义的 Runtime 无关端口，只声明能力探测、Session
生命周期、消息、规范化事件流、Run、Job、项目访问配置、项目访问验证和统一错误。
项目访问端口接收规范化的 MCP Endpoint、待写入凭证和期望能力，不得包含 Hermes
API 路径、Dashboard、Cloudflare、SSE 事件名、Profile 或 Hermes 凭证，也不负责
持久化 Agent、管理模式、Project Grant、Token 状态或 Session 映射。

Adapter 注册元数据必须分别声明 `project_access.verify`、
`project_access.configure` 和 `project_access.rotate`。`manual` 只依赖验证能力；只有
实现层声明三项能力时设置页才展示 `auto`。用户填写管理地址后还要执行实例级能力
探测，全部通过才允许激活自动管理。未来其他 Runtime 由各自 Adapter 实现自己的
管理协议和认证类型，不能把 Cloudflare Access 或 Hermes Dashboard 提升为通用
`AgentAdapter` 概念。

v0.1 和 Stage 5 **只实现 `HermesAdapter`**，不同时实现其他 Agent Adapter。
`HermesAdapter` 负责使用 Hermes API Server 和 API Key 实现上述端口，将统一操作
映射到 Hermes Sessions、Runs、SSE 和 Jobs API，并处理 Hermes 能力探测、版本兼容
和错误转换。在自动管理模式下，它还通过 Hermes Dashboard 管理 API 实现 mmdash
MCP 的创建、更新、测试、凭证写入及 Gateway reload/restart；Dashboard Session
Token、Cloudflare Access 探测和对应请求头都封装在 `HermesAdapter` 内。新增其他
Runtime 必须提供新的 Adapter 实现，不能把供应商分支加入 `AgentAdapter` 或
`HermesAdapter`。

Agent 模块拥有 Agent 实例、Adapter 类型、`management_mode`、Project Grant、Session
索引、远端 ID 映射和生命周期；v0.1 的 Adapter 类型只允许 `hermes`，管理模式只
允许 `manual` 或 `auto`。Auth 模块拥有 Agent Token 的生成、Hash、验证、重叠轮换
和撤销。首版 Agent Token 为高熵 opaque Token，绑定单个 Agent 实例、Project 和
允许的 Tool；明文只在创建或轮换时返回一次。Hermes 使用该 Token 直接连接 MCP
Gateway；CLI 不参与 Agent Token 的签发、保存或运行时转发。

每枚 `pending` Agent Token 同时生成独立的高熵单次 challenge，Core 只保存 Hash；
一次性配置材料将 challenge 放在 MCP endpoint 查询参数中。Hermes 使用该 endpoint
和同一枚 pending Agent Token 完成协议协商及精确 `tools/list` 后，Gateway 把原始
Agent Token 与 challenge 传给 Core。Core 核对 Token、Agent、Project 和 challenge
Hash 并原子消费 challenge 后记录证据；不需要 Gateway API Token 或 relay attestation。

管理模式的语义固定为：

| 模式 | Agent 模块 | `HermesAdapter` | 管理凭证 |
| --- | --- | --- | --- |
| `manual` | 签发 Token、展示一次性配置材料、等待验证并维护轮换状态 | 验证运行时和已存在的 MCP 连接，不修改 Hermes | 不保存；Dashboard URL 仅为可选跳转链接 |
| `auto` | 编排首次配置和两阶段轮换事务 | 通过 Dashboard 管理 API 配置 MCP、写入 Token、reload/restart 并验证 | 加密保存 Dashboard Session Token；仅在需要 Cloudflare Access 时保存其 Service Token |

`auto` 的网络类型不是用户预先固定选择的供应商枚举。HermesAdapter 从服务端运行
环境探测 `management_url`：管理 API 可直接访问时记录为 `direct`；检测到 Cloudflare
Access 挑战时记录为 `cloudflare_access` 并要求 Client ID/Client Secret；其他结果
标记为 `unreachable` 或 `unsupported_auth`，拒绝开启自动管理。探测结果需要持久化
最后状态和时间，但每次连接测试都必须重新验证，不能只依赖地址字符串推断。

`direct` 仅表示 HermesAdapter 所在进程可以访问目标地址。服务端的 `127.0.0.1` 与
用户电脑的 `127.0.0.1` 不是同一地址；远端 mmdash 访问用户本地 Hermes 时仍需要
同机部署、可路由内网、VPN 或 Tunnel。Cloudflare Access 只控制外层网络访问，
Hermes Dashboard Session Token 仍用于敏感 Dashboard API，二者不能互相替代。

`management_url` 是受控 Connector 出站目标，必须执行 SSRF 防护：只接受允许的
HTTP(S) scheme 和端口；禁止 URL 内嵌凭证；每次 DNS 解析和重定向都重新校验目标；
默认拒绝 link-local、云元数据地址和未授权私网；loopback/私网仅在部署级策略明确
允许且目标通过 Hermes 管理 API 身份探测时开放。连接池不得跨 Agent 实例复用认证
上下文；探测、配置、凭证写入和重启操作必须设置超时、速率限制、结构化脱敏日志
和 Audit。

Hermes API Key、Hermes Dashboard Session Token、可选的 Cloudflare Access Service
Token 和 mmdash Agent Token 分别代表运行时调用、Hermes 管理、外层网络访问和
Project 数据访问。Settings 模块负责前三类配置密钥的信封加密、脱敏和读取授权；
Auth 模块只负责 mmdash Agent Token。浏览器保存后不得重新读取任何明文。

Agent Token 轮换使用 `pending -> active -> revoked` 的两阶段状态，而不是原地覆盖：

1. Auth 签发 `pending` 新 Token，旧 `active` Token 继续有效。
2. `manual` 等待用户写入并验证；`auto` 调用 `HermesAdapter` 写入新 Token，必要时
   reload 或重启 Gateway。
3. 使用新 Token 和单次 challenge 完成协商后的精确 `tools/list`，由 Core 记录证据并消费 challenge 后，将新 Token 设为 `active` 并撤销旧 Token。
4. 任一步骤失败则保留旧 Token，撤销或保留待重试的新 Token，并记录
   `rotation_failed`；禁止先撤销旧 Token。

Agent 域能力：

- Session 索引、类型、状态和项目映射；
- `manual / auto` 管理模式、配置状态和 Token 轮换状态；
- 统一的消息、事件、Run 和 Job 模型；
- 停止和重新执行工作流；
- 项目专用提示词；
- Adapter 选择与能力校验。

Agent 页面使用 viewport 填充的三栏工作台，左右栏独立折叠，聊天区内部滚动并对
overscroll 做隔离。非终态 Run 在重新进入页面时按本地 Run ID 重新附着 SSE；页面只
展示安全的 reasoning 可用/运行状态和规范化 Tool Call 摘要，不返回私有思维链。
Agent 实例删除采用 `removed_at` 逻辑移除并撤销 Grant/Token，历史记录不级联删除。

精确 Tool `artifact.upload` 通过 Gateway 把原始 Agent Token 传到私网 Core 的专用
Agent Artifact 初始化端点。Core 固定 `kind/source=agent`，记录签发用户和具体
`agent_instance_id`；Gateway 只返回可由 Hermes 访问的对象存储分片 PUT 授权，不接收
文件字节或 base64，确认阶段由 Core 校验大小、SHA-256 和全部 ETag。

对话文件通过 `artifact_relations(target_type=agent_run)` 建立来源：浏览器附件使用
`attachment` 输入关系，携带经校验 Session/Run 的 Agent 上传使用 `output` 输出关系。
精确 Tool `artifact.read` 复用 Core 的 Artifact RBAC 与短时下载授权，让 Hermes 读取
用户附件；Web 依据关系渲染文件卡片/图片预览，而不是解析模型文本中的本地路径。

Hermes 的远端 Session ID 只作为稳定映射，不作为模型记忆保证。每次启动 Run 前，Core
读取远端消息并把最新的有界用户/助手对话显式传给 Adapter；终态后持久化消息与 SSE
草稿按消息内容/ID 收敛，避免最终回复和工具调用重复展示。

Hermes 专属实现能力：

- Hermes Sessions、Runs、SSE 和 Jobs API 映射；
- Hermes 健康、Token、版本、能力和 MCP 完整检查；
- 手动模式的可选 Dashboard 配置入口；
- 自动模式的 Dashboard 管理 API、管理地址可达性与认证探测；
- `direct` 管理链路，以及需要时的 Cloudflare Access Service Token 链路；
- MCP 凭证写入、验证和 Gateway reload/restart。

自动进度跟踪首版同时支持：

```
Cron（mmdash Core / PostgreSQL 调度）
+ Commit/领域事件
+ 手动重新评估
```

输入包括题目、约束、节点、TODO、Repo Commit、Artifact、Model Snapshot、Experiment、Article、显式上下文和上次评估。

输出包括阶段、摘要、变化、完成项、进行项、阻塞、风险、建议任务和待确认问题。

必须实现防抖、事件合并、最短评估间隔、项目级开关、历史、Proposal 和首页同步。

## 5.11 `backend/internal/model/`

拥有 Notion Source、同步任务、Snapshot、Hash、Diff、Tag 和版本说明。

Hash 不变不创建新 Snapshot。Notion 内容解析由 Worker 完成；Model 保存规范化结果和版本关系。

## 5.12 `backend/internal/experiment/`

拥有 Exp ID、状态机、冻结参数、source commit、entrypoint、运行申请、日志引用、结果验证、分析和归档。

约束：

- 一个 Exp ID 只允许成功启动一次；
- 不允许任意 Shell；
- 参数和 source commit 创建后冻结；
- 一个 Exp 对应零或一个主结果包；
- 失败保留日志但无成功结果指针；
- 主结果包为 standalone `artifact.zip`。

```
artifact.zip
├── manifest.json
├── summary.md
├── logs/
├── figures/
├── tables/
├── data/
└── models/
```

## 5.13 `backend/internal/boxcontrol/`

负责 mmdash Core 侧的 Box 注册、Token、心跳、状态、Capability、负载、项目绑定、任务调度和结果接收。

Box 是由 Box Gateway 和其内部 Capability 组成的能力节点；Sandbox 只是首项 Capability。

## 5.14 `backend/internal/article/`

拥有 Article Workspace、Block、Patch、Tag、Reference、Commit、Build 和 Release。

规则：

- Markdown 是唯一可编辑源；仅 `manuscript.md`、`references.bib` 和 `.mmdash/article.json` 进入 Repo article branch；
- BFF 承载单实例 Hocuspocus/Yjs 协作边界并只通过生成 Core Client 持久化；Core 拥有 draft revision、Yjs 状态、块和 Markdown 投影；v0.1 不引入 Redis；
- Commit 通过 flush/state-vector/revision 屏障调用 Repo `ArticleWorkspace`，后到编辑不会进入既有 Commit；
- 生成 LaTeX、PDF、源码 ZIP、Build Report、日志和 SyncTeX 都是不可变 Artifact Version；
- Preview 绑定草稿 revision 且 latest-only，正式 Build 只绑定 Commit；
- Build 可针对任意历史 Commit；
- 同一 Commit 可多次 Build；
- 失败 Build 不覆盖成功产物；
- Release 绑定指定 Commit、一次成功 Build 与具体输出 Artifact Version，创建后不可修改；
- Reference 固定来源对象 ID 和版本。

## 5.15 `backend/internal/jobs/`

PostgreSQL Job Queue：

- 创建、领取、锁定、续租、重试、取消和超时；
- `FOR UPDATE SKIP LOCKED`；
- Worker 心跳；
- Handler 注册；
- 日志和结果提交；
- 幂等键。

## 5.16 `backend/internal/audit/`

记录认证、权限、设置、Git、Artifact、MCP、Agent、Notification、Experiment、Box、Article 和敏感下载操作。

## 5.17 `backend/internal/platform/`

保存数据库、事务、对象存储、Event Bus、Outbox、日志、ID、时间、分页、错误和模块注册等基础设施实现。

重要业务变更必须在同一事务中写业务状态和 `system_outbox`。

## 5.18 `backend/pkg/`

仅保存真正稳定且可被外部 Go 组件复用的库。优先使用 `internal/`，避免过早公共化。

## 5.19 `backend/migrations/`

每个领域模块拥有自己的 Migration 文件和表前缀。禁止一个模块的 Migration 修改另一个模块的数据语义。

# 6. `workers/`

Worker 使用 Python，负责长耗时、格式转换和第三方内容解析，不拥有领域状态。

## 6.1 `workers/mmdash-worker/jobs/`

Job 拉取、续租、取消、日志、结果提交和 Handler 注册。

## 6.2 `workers/mmdash-worker/notion/`

- Notion 页面、公式、表格和图片解析；
- 规范化 Markdown/AST；
- Snapshot 内容生成；
- 解析失败报告。

## 6.3 `workers/mmdash-worker/latex/`

- Markdown → LaTeX；
- 模板应用；
- PDF Build；
- Build Report；
- 日志和中间文件归档。

## 6.4 `workers/mmdash-worker/preview/`

- 图片、PDF、CSV、JSON、文本预览；
- 缩略图；
- 结构摘要；
- `SemanticDescriptionGenerator` 接口占位。

Stage 2 不调用 LLM 或多模态服务，也不自动生成描述和 `recommended_usage`；
这些语义能力在 Article 阶段实现。

## 6.5 `workers/mmdash-worker/analysis/`

- 实验结果摘要；
- 多实验比较数据预处理；
- Agent Context Package 准备；
- 非权威分析结果生成。

Worker 只通过 Job API 领取任务和提交结果，不直接更新业务表。

# 7. `box/`

`box/` 保存独立部署的 mmdash Box 实现。Box 是注册到 mmdash 的能力节点，由 Box Gateway 及其内部 Capability 组成。

## 7.1 `box/gateway/`

职责：

- 注册与认证；
- 心跳、状态、负载和版本；
- Capability 注册；
- 接收标准实验任务；
- 创建和销毁环境；
- 拉取固定 commit；
- 注入只读输入和短期凭证；
- 日志和状态流；
- 收集 Artifact；
- 按 manifest 提取并回传 `artifact.zip`。

## 7.2 `box/capabilities/sandbox/`

Sandbox 是首版 Capability，负责：

- 运行预定义镜像；
- 固定入口和冻结参数；
- CPU、内存、时间和网络限制；
- stdout/stderr；
- 产物目录收集；
- 任务结束销毁环境。

Sandbox 不负责写代码、改参数、提交 Git 或保存长期 Workspace。

## 7.3 `box/runtimes/local-docker/`

首个开发和联调 Runtime：本地 Docker 容器、挂载隔离、资源限制和日志收集。

## 7.4 `box/runtimes/e2b/`

E2B 是首版正式 Runtime Adapter，而不是 Box 本身。它必须实现与 Local Docker 相同的 `SandboxRuntime` 接口，并完成创建、执行、日志、文件提取、超时和销毁验收。

## 7.5 `box/contracts/`

保存 Box Gateway 与 Core 间的任务、心跳、Capability、日志、状态和 Artifact 回传契约。

# 8. `deploy/`

## 8.1 `deploy/compose/`

首版本地和单机部署：Web、BFF、MCP Gateway、Core、Worker、PostgreSQL、MinIO、Caddy。Box 可本地同机，也可远程注册。

## 8.3 `deploy/postgres/`

```
MCP Agent 流量
Box 节点流量
内部 Worker 流量
```
