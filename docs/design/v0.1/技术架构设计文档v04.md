# 技术架构设计文档 v0.4

> 本文档是 `设计文档 v0.1` 的技术实现细化与扩展。原设计中的产品功能、交互、约束和首版范围全部保留；本文新增的模块化单体、BFF、OpenAPI、Job Queue、Outbox、Artifact、RBAC、Data Hub 和多 Runtime 设计用于支撑原功能，不得反向裁剪原设计。
> 

**首版技术组合**

```
Caddy
+ Next.js Web
+ TypeScript Web BFF
+ TypeScript MCP Gateway
+ 本地 CLI / stdio MCP
+ Go 模块化单体 Core
+ Python Worker
+ Go Box Gateway
+ PostgreSQL
+ MinIO / S3
```

**核心调用边界**

```
Browser → Web BFF → Core Server
Codex / Claude Code → clients/cli（stdio MCP）→ MCP Gateway → Core Server
Hermes API Server ↔ Agent Adapter；Hermes → MCP Gateway → Project Data Hub
Core Jobs ↔ Python Worker
Core Box Control ↔ Box Gateway → Capability → Runtime
```

Web BFF、MCP Gateway、CLI、Worker 和 Box 均不得直接写业务数据库；权威业务状态由 Go Core Server 管理。

# 1. `apps/`

`apps/` 保存长期运行、可独立部署的 Web 与服务端接入应用。它们负责交互、认证、聚合和协议转换，不拥有核心领域状态。

## 1.1 `apps/web/`

技术：Next.js、React、TypeScript、Tailwind CSS、shadcn/ui、TanStack Query、Zustand、TipTap、Monaco Editor、ECharts。

一级导航保持原设计七项：

1. 首页；
2. mmdash Agent；
3. 进度跟踪；
4. 模型版本；
5. 论文写作；
6. 求解记录；
7. 设置。

Repo 和 Artifact 是独立功能模块，但不增加一级导航：Repo 的连接和分支配置进入设置页，代码树进入求解记录和引用组件；Artifact 通过首页、论文、模型和求解页面中的共享文件抽屉、附件库和选择器访问。

建议结构：

```
apps/web/src/
├── app/
│   ├── login/
│   ├── projects/
│   │   └── [projectId]/
│   │       ├── page.tsx
│   │       ├── agent/
│   │       ├── progress/
│   │       ├── models/
│   │       ├── article/
│   │       ├── experiments/
│   │       └── settings/
│   └── layout.tsx
├── features/
├── components/
├── hooks/
└── lib/
```

### 1.1.1 首页

必须展示：

- 题目卡片：标题、原始题目文件、关键约束；
- 当前阶段：Agent 判断结果，允许人工修正；
- 关键节点：最近截止时间和延期状态；
- TODO：今日、逾期、阻塞；
- 模型摘要：最新 Snapshot 和最近变化；
- 实验摘要：运行中、成功、失败和最新结果；
- 论文摘要：章节完成度、未审阅块、最近 Release；
- Agent 状态：Hermes 连接和最近进度评估时间。

每个摘要都必须可跳转到对应对象。数据由 Data Hub 聚合，不要求重复录入。

### 1.1.2 mmdash Agent 页面

必须支持：

- 创建、切换、重命名、结束、继续和分叉 Session；
- `main / progress / experiment` 三类 Session；
- 默认 Session；
- 消息历史、流式回复、工具调用、Run 状态；
- 停止、重新生成、重新执行；
- Hermes 连接状态和管理面板入口；
- 项目专用提示词自动生成、手工修改、恢复默认；
- 自动进度跟踪开关；
- Cron、事件触发任务、最近执行结果；
- 手动“重新评估进度”。

Hermes 保存完整消息历史；mmdash 保存 Session 索引、项目映射、名称、类型和状态。

### 1.1.3 进度跟踪页面

- 人工关键时间节点；
- TODO、负责人、来源、关联对象、时间和依赖；
- 看板：待办、进行中、阻塞、完成；
- 列表；
- 日历/甘特；
- 今日视图；
- 提醒和外部通知；
- Proposal 审阅。

关键节点未经人工确认不得由 Agent 修改。普通 TODO 默认允许 Agent 调整，也可在项目设置中切换为仅 Proposal。

### 1.1.4 模型版本页面

- 左侧版本时间线；
- 中间版本渲染；
- 右侧元数据、标签和说明；
- 两版本 Diff；
- 手动同步；
- 可选定时同步；
- Hash 不变时不创建 Snapshot；
- 不在 mmdash 中重做复杂模型编辑器。

### 1.1.5 论文写作页面

布局：左侧参考区，右侧块级 Markdown 编辑器，右上角显示 LaTeX 状态、Build 历史和 Markdown Commit 历史。

块级编辑器必须支持：

- 标题、段落、图片、表格、公式独立成块；
- 稳定 `block_id`；
- 拖拽排序和组合；
- `/` 命令；
- AI 修改以 Patch 呈现；
- 接受或拒绝 Patch；
- 行/块 Tag 和章节 Tag；
- Git 状态式颜色。

Tag：

```
章节tag：未编辑 / 未审阅 / 已审阅
块tag：AI 初稿 / 人工初稿 / AI 修订 / 人工修订 / 已审阅
```

附件进入注册表，至少保存：

```
attachment_id
filename
sha256
mime_type
description
source
created_at
recommended_usage[]
status
```

Markdown Commit 时可选择生成 LaTeX，也可对历史 Commit 单独 Build。同一 Commit 可以多次 Build；Release 绑定任意 Commit 的一次成功 Build。

### 1.1.6 求解记录页面

实验列表显示 Exp ID、名称、状态、创建者、时间和 source commit。

详情必须包含：

- 参数、环境、日志、失败原因、资源消耗和结果摘要；
- 代码快照或结果包文件树；
- 文本、图片、表格、JSON、CSV 和日志预览；
- AI/人工结果分析；
- 多实验比较；
- 有限文本编辑；
- 外部编辑器入口；
- 项目绑定且活跃的 Box。

点击 Box 可查看在线状态、负载、Gateway 版本、Capability、Runtime 和资源限制，并跳转设置页绑定、解除或更换 Box。

### 1.1.7 设置页

模块通过插槽注册设置：

- Project：题目、约束、成员和角色；
- Repo：Provider、仓库、三个分支和 Webhook；
- Artifact：对象存储和上传限制；
- Agent：Hermes 和自动进度跟踪；
- Progress：通知渠道；
- Model：Notion；
- Article：Zotero、LaTeX 模板和论文规范；
- Experiment：Box、Runtime、资源和超时；
- MCP/CLI：Token、默认项目和仓库绑定。

## 1.2 `apps/web-bff/`

技术：TypeScript、Node.js、Fastify、Zod、Pino、OpenAPI 生成的 Core Client。

职责：

- 浏览器认证；
- 当前用户和项目上下文；
- 页面级 API；
- Core API 聚合；
- 页面 DTO 转换；
- 错误转换；
- SSE、WebSocket 和文件流代理；
- 隐藏 Core 内部模块结构。

BFF 不直接访问 PostgreSQL、MinIO、Git、Hermes 或 Box，不生成 Exp ID，不实现领域状态机。

## 1.3 `apps/mcp-gateway/`

使用 TypeScript 和官方 MCP SDK，以 Streamable HTTP 向 CLI、Hermes 和外部 Agent 暴露受控能力。

首版 Tool：

```
project.list
project.get
data.list
data.read
experiment.create
experiment.run
experiment.status
result.get
context.promote
progress.recalculate
```

职责：

- MCP Session；
- CLI Token 和 Agent Token；
- Tool 注册、参数校验和权限；
- 项目解析；
- Core API 转发；
- MCP 错误转换；
- 审计。

MCP Gateway 不直接读取 Git、对象存储或业务数据库。

# 2. `clients/`

`clients/` 保存安装在用户设备上的客户端。它与 `apps/` 分离，因为 CLI 不是长期运行的服务，也不是服务端部署单元。

## 2.1 `clients/cli/`

CLI 是 Codex、Claude Code 等本地 Coding Agent 连接 mmdash 的入口，同时提供人工命令行操作。

建议结构：

```
clients/cli/
├── src/
│   ├── commands/
│   │   ├── login.ts
│   │   ├── project-list.ts
│   │   ├── project-use.ts
│   │   ├── project-bind.ts
│   │   └── mcp.ts
│   ├── auth/
│   ├── config/
│   ├── credentials/
│   ├── mcp/
│   └── main.ts
├── package.json
└── tsconfig.json
```

首版命令：

```
mmdash login
mmdash logout
mmdash project list
mmdash project use <project_id>
mmdash project bind
mmdash project current
mmdash mcp
mmdash doctor
```

`mmdash mcp` 启动本地 stdio MCP Server，将请求通过 HTTPS / MCP Streamable HTTP 转发给 `apps/mcp-gateway/`。

调用链：

```
Codex / Claude Code
        ↓ stdio MCP
clients/cli
        ↓ HTTPS / MCP Streamable HTTP
apps/mcp-gateway
        ↓ Core OpenAPI
backend/cmd/core-server
```

CLI 负责：

- 登录和 Token 刷新；
- 系统安全凭证存储；
- 默认项目；
- 当前本地仓库与项目绑定；
- stdio 与远程 MCP 的桥接；
- 网络、认证和项目歧义诊断；
- 项目不明确时拒绝执行写操作。

CLI 不保存权威项目数据，不直接访问数据库、Git Provider、MinIO 或 Box。

# 3. `packages/`

`packages/` 保存 TypeScript 应用和客户端共享的库，不承载独立部署和业务所有权。

## 3.1 `packages/core-client/`

由 OpenAPI 生成的 Core Client，供 Web BFF、MCP Gateway 和必要的内部工具使用。

## 3.2 `packages/api-types/`

共享 API DTO、分页、错误、ID 和时间类型。只允许引用生成或稳定公共类型，不复制领域实现。

## 3.3 `packages/auth/`

浏览器、CLI、Agent 和服务间 Token 的通用处理；不拥有用户和权限数据。

## 3.4 `packages/validation/`

Zod/JSON Schema 公共校验、错误格式化和输入标准化。

## 3.5 `packages/errors/`

跨 TypeScript 应用共享错误码、用户消息和可重试标志。

## 3.6 `packages/logging/`

Pino 配置、字段约定、脱敏和 request_id 传播。

## 3.7 `packages/mcp-client/`

CLI、Hermes 相关接入和测试工具共享的 MCP Streamable HTTP Client。CLI 的 stdio Server 本体仍在 `clients/cli/`。

## 3.8 `packages/ui/`

Web 通用 UI 组件，包括文件树、日志、Diff、时间线、Markdown、表格和状态展示。

# 4. `contracts/`

`contracts/` 保存跨进程、跨语言、跨仓库边界的稳定契约，是生成代码和契约测试的唯一来源。

## 4.1 `contracts/openapi/`

- Core OpenAPI；
- Web BFF 可选公开 API；
- Box Control API；
- 版本和兼容策略；
- TypeScript Client 与 Go Handler 类型生成。

## 4.2 `contracts/events/`

统一事件信封：

```
event_id
event_type
schema_version
occurred_at
producer
project_id
actor
correlation_id
causation_id
payload
```

首版重要事件：

```
repo.commit.created
artifact.created
artifact.available
progress.task.updated
progress.proposal.created
agent.progress.evaluated
model.snapshot.created
experiment.created
experiment.started
experiment.succeeded
experiment.failed
experiment.archived
article.commit.created
article.build.completed
article.release.created
box.registered
box.heartbeat.received
```

## 4.3 `contracts/json-schema/`

保存 Experiment Manifest、Artifact Pointer、Box Capability、Agent 评估结果、Context Proposal 等结构。

# 5. `backend/`

`backend/` 是 Go 模块化单体和权威业务数据的所在地。模块之间通过应用服务、只读查询接口和领域事件协作，禁止直接写其他模块表。

## 5.1 `backend/cmd/core-server/`

- 配置加载；
- HTTP Server；
- 模块注册；
- PostgreSQL、MinIO、Job Queue 初始化；
- 健康检查；
- 优雅退出；
- OpenAPI 暴露。

## 5.2 `backend/internal/auth/`

拥有用户、登录、Session/JWT、API Token、Agent Token、Box Token、撤销和身份上下文。

首版角色：

```
owner maintainer editor viewer agent box
```

## 5.3 `backend/internal/project/`

拥有项目、成员、角色、归档、题目结构化信息和关键约束。

```
problem_title
problem_summary
project_constraints[]
source_artifact_ids[]
```

原始题目文件由 Artifact 管理，Project 只保存引用。

## 5.4 `backend/internal/settings/`

拥有系统级和项目级配置、密钥加密、脱敏、模块设置注册和连接测试规范。具体 Git、Hermes、Notion、Zotero、通知、Box 配置由所属模块定义。

## 5.5 `backend/internal/repo/`

Repo 是独立功能模块和所有 Git 操作的唯一入口。

首版：

- 一个项目默认一个 Git Repo；
- `code / article / result` 三个分支；
- Worktree 并行访问；
- Provider、状态、分支、Commit、文件树和文件内容；
- Webhook；
- 临时 Checkout；
- 有限文本编辑；
- article/result 提交；
- `ArticleWorkspace` 抽象，允许未来独立 article repo。

发布 `repo.commit.created/detected`，供 Agent、Model、Experiment、Article 和 Data Hub 消费。

## 5.6 `backend/internal/artifact/`

Artifact 是独立模块，统一管理题目文件、普通附件、预览、构建产物和实验结果包。

拥有：

- 元数据、Hash、MIME、大小、来源和状态；
- Signed URL；
- Local、MinIO、S3 Adapter；
- 附件注册表；
- 预览索引；
- 来源对象关联；
- 小型 Git Artifact 与大型对象存储 Pointer。

## 5.7 `backend/internal/progress/`

拥有 Milestone、Task、Dependency、Reminder 和 Proposal。

规则：

- 关键节点由人创建，Agent 只能提出 Proposal；
- 普通 TODO 可配置为 Agent 自动调整或仅 Proposal；
- 提醒通过 NotificationAdapter 发送；
- 看板、列表、甘特和今日视图读取同一权威数据。

## 5.8 `backend/internal/datahub/`

Data Hub 是跨模块统一读取和项目上下文层，不替代各模块的权威数据。

拥有：

- Stable Object ID；
- Object Registry；
- Activity Timeline；
- Project Context；
- Context Proposal；
- `data.list` 和 `data.read` 路由；
- 首页聚合投影。

各模块通过事件更新投影，并实现完整对象读取 Adapter。

## 5.9 `backend/internal/agent/`

通过 `AgentAdapter` 对接 Hermes，首版实现 `HermesAdapter`。

会话能力：

- Session 索引、类型、状态和项目映射；
- Runs API、SSE、停止和重新执行；
- Jobs API；
- 项目专用提示词；
- Hermes 健康、Token、Session、Run、Jobs 和 MCP 完整检查。

自动进度跟踪首版同时支持：

```
Cron（Hermes Jobs API）
+ Commit/领域事件
+ 手动重新评估
```

输入包括题目、约束、节点、TODO、Repo Commit、Artifact、Model Snapshot、Experiment、Article、显式上下文和上次评估。

输出包括阶段、摘要、变化、完成项、进行项、阻塞、风险、建议任务和待确认问题。

必须实现防抖、事件合并、最短评估间隔、项目级开关、历史、Proposal 和首页同步。

## 5.10 `backend/internal/model/`

拥有 Notion Source、同步任务、Snapshot、Hash、Diff、Tag 和版本说明。

Hash 不变不创建新 Snapshot。Notion 内容解析由 Worker 完成；Model 保存规范化结果和版本关系。

## 5.11 `backend/internal/experiment/`

拥有 Exp ID、状态机、冻结参数、source commit、entrypoint、运行申请、日志引用、结果验证、分析和归档。

约束：

- 一个 Exp ID 只允许成功启动一次；
- 不允许任意 Shell；
- 参数和 source commit 创建后冻结；
- 一个 Exp 对应零或一个主结果包；
- 失败保留日志但无成功结果指针；
- 主结果包为 standalone `artifact.zip`。

```
artifact.zip
├── manifest.json
├── summary.md
├── logs/
├── figures/
├── tables/
├── data/
└── models/
```

## 5.12 `backend/internal/boxcontrol/`

负责 mmdash Core 侧的 Box 注册、Token、心跳、状态、Capability、负载、项目绑定、任务调度和结果接收。

Box 是由 Box Gateway 和其内部 Capability 组成的能力节点；Sandbox 只是首项 Capability。

## 5.13 `backend/internal/article/`

拥有 Article Workspace、Block、Patch、Tag、Reference、Commit、Build 和 Release。

规则：

- Markdown 和生成的 LaTeX 进入 Git；
- Build 可针对任意历史 Commit；
- 同一 Commit 可多次 Build；
- PDF 和 Build Report 登记为 Artifact；
- 失败 Build 不覆盖成功产物；
- Release 绑定指定 Commit 和一次成功 Build；
- Reference 固定来源对象 ID 和版本。

## 5.14 `backend/internal/jobs/`

PostgreSQL Job Queue：

- 创建、领取、锁定、续租、重试、取消和超时；
- `FOR UPDATE SKIP LOCKED`；
- Worker 心跳；
- Handler 注册；
- 日志和结果提交；
- 幂等键。

## 5.15 `backend/internal/audit/`

记录认证、权限、设置、Git、Artifact、MCP、Agent、Experiment、Box、Article 和敏感下载操作。

## 5.16 `backend/internal/platform/`

保存数据库、事务、对象存储、Event Bus、Outbox、日志、ID、时间、分页、错误和模块注册等基础设施实现。

重要业务变更必须在同一事务中写业务状态和 `system_outbox`。

## 5.17 `backend/pkg/`

仅保存真正稳定且可被外部 Go 组件复用的库。优先使用 `internal/`，避免过早公共化。

## 5.18 `backend/migrations/`

每个领域模块拥有自己的 Migration 文件和表前缀。禁止一个模块的 Migration 修改另一个模块的数据语义。

# 7. `box/`

`box/` 保存独立部署的 mmdash Box 实现。Box 是注册到 mmdash 的能力节点，由 Box Gateway 及其内部 Capability 组成。

## 7.1 `box/gateway/`

职责：

- 注册与认证；
- 心跳、状态、负载和版本；
- Capability 注册；
- 接收标准实验任务；
- 创建和销毁环境；
- 拉取固定 commit；
- 注入只读输入和短期凭证；
- 日志和状态流；
- 收集 Artifact；
- 按 manifest 提取并回传 `artifact.zip`。

## 7.2 `box/capabilities/sandbox/`

Sandbox 是首版 Capability，负责：

- 运行预定义镜像；
- 固定入口和冻结参数；
- CPU、内存、时间和网络限制；
- stdout/stderr；
- 产物目录收集；
- 任务结束销毁环境。

Sandbox 不负责写代码、改参数、提交 Git 或保存长期 Workspace。

## 7.3 `box/runtimes/local-docker/`

首个开发和联调 Runtime：本地 Docker 容器、挂载隔离、资源限制和日志收集。

## 7.4 `box/runtimes/e2b/`

E2B 是首版正式 Runtime Adapter，而不是 Box 本身。它必须实现与 Local Docker 相同的 `SandboxRuntime` 接口，并完成创建、执行、日志、文件提取、超时和销毁验收。

## 7.5 `box/contracts/`

保存 Box Gateway 与 Core 间的任务、心跳、Capability、日志、状态和 Artifact 回传契约。

# 8. `deploy/`

## 8.1 `deploy/compose/`

首版本地和单机部署：Web、BFF、MCP Gateway、Core、Worker、PostgreSQL、MinIO、Caddy。Box 可本地同机，也可远程注册。

## 8.2 `deploy/caddy/`

```
/       → Web
/api/*  → Web BFF
/mcp/*  → MCP Gateway
/box/*  → Core Box Endpoint
```

支持 HTTPS、SSE、WebSocket、文件大小限制、访问日志和安全 Header。

## 8.3 `deploy/postgres/`

初始化、Migration、备份、恢复、连接池和健康检查。

## 8.4 `deploy/minio/`

Bucket、生命周期、Signed URL、备份和大型 Artifact 管理。

部署必须显式区分：

```
Web 用户流量
MCP Agent 流量
Box 节点流量
内部 Worker 流量
```
