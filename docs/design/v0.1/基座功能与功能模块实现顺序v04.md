# 1. 开发方式

采用“共同完成技术基座，之后按功能模块纵向开发”的方式。

```
全员共同完成技术基座
        ↓
依次完成 P0 前置功能模块
        ↓
由开发者纵向负责主要业务模块
        ↓
打通跨模块数据、事件和完整产品闭环
```

一个功能模块的完整纵向范围包括：

```
Web 页面与交互
→ Web BFF 路由
→ Core OpenAPI
→ Core 领域模块
→ 数据库 Migration
→ Settings 扩展
→ Adapter / Worker / Box Runtime
→ 领域事件与 Outbox
→ Data Hub 投影和 data.read
→ MCP Tool / CLI 支持
→ Audit
→ 单元测试、集成测试、契约测试、端到端测试
→ 模块文档
```

某模块确实不需要 Worker、MCP Tool 或外部 Adapter 时可以省略，但必须在模块文档中明确说明。不能只完成后端接口而不实现原设计中的页面、交互和完整用户流程。

Repo、Artifact 和 CLI/MCP 是 **P0 前置功能模块**，不是技术基座。它们必须先纵向完成，因为后续模块都依赖项目版本、统一文件对象和本地 Coding Agent 接入。Hermes 等独立 Agent Runtime 的产品级身份、Agent Token 和直连 MCP Gateway 在后续 Agent 阶段实现。

## 3.16 登录、注册与成员邀请闭环

3.8 已提供 Session/JWT、登录接口与 bootstrap 账号，但技术基座只有内置管理员可登录，缺少自助注册与成员邀请，无法支撑多人协作。本阶段把 Auth 从“单个内置账号可登录”补齐为“可注册、可登录、可邀请、可管理”的完整身份闭环，为 Repo、Artifact 等 P0 模块提供真实的多用户与角色基础。成员与角色的权限语义沿用 3.8 RBAC。

### 账号与注册

- 自助注册：邮箱 + 密码注册，邮箱唯一（不区分大小写），注册即激活并可直接登录；
- 开放注册为系统级设置（`auth.allow_open_registration`），本地/单机默认开启，生产可关闭切换为纯邀请制；
- bootstrap 管理员仍由 `EnsureBootstrapUser` 保证存在，作为邀请制下的种子账号；
- 密码哈希、强度校验与错误信息脱敏复用 3.8 与 3.14 规范。

### 登录与会话闭环

- 登录、登出、`/auth/me` 已在 3.8 提供，本阶段补齐前端闭环：登录页、注册页、未登录路由守卫（中间件）与会话失效后跳回登录并回跳原页面；
- Web 经 BFF 下发会话 Cookie，受保护页面统一由守卫拦截，不再依赖逐页 401 兜底。

### 成员邀请闭环

- 邀请发起：owner / maintainer 可按邮箱邀请成员并指定角色（owner / maintainer / editor / viewer / agent / box）；
- 邀请载体：生成一次性、带过期时间的邀请 Token；已注册用户接受后直接加入，未注册用户凭邀请完成注册并加入；
- 接受与撤销：接受后建立成员关系并写入角色；发起方或管理员可撤销未接受的邀请；
- 成员管理：项目成员列表、角色变更与移除，全部经过 RBAC 校验；
- 幂等与并发：同一邮箱对同一项目的有效邀请幂等，Token 一次性使用、过期失效。

## 3.17 通知模块（内部和外部通知）

3.12 已提供 Event Bus、Outbox、消费幂等和重放，3.9 已提供项目级设置、密钥加密与连接测试。本阶段在其上建立统一 Notification 底座：内部通知以用户收件箱形式可靠保存，外部通知按项目配置投递到飞书、Webhook 等渠道。业务模块只发布领域事件或调用类型化通知用例，不直接写通知表，也不直接调用外部渠道。

### 目标与领域边界

Notification 是通知意图、用户收件关系、站内状态和外部投递状态的唯一权威模块，但不是来源业务对象的权威模块。

- Project 继续拥有邀请、成员和角色；Progress 继续拥有 Reminder、Milestone 和 Task；Experiment、Article 等模块继续拥有各自状态；
- Notification 通过稳定领域事件获知变化，只保存来源事件和资源引用，不直接写 Auth、Project、Progress 或其他模块表；
- 接受邀请、完成任务、重试实验等动作必须调用来源模块的命令接口，由来源模块重新检查身份、权限、有效期和并发状态；
- 收件箱阅读状态、通知业务结果和外部投递结果是三个独立维度，不使用一个 `status` 字段混合表达；
- 外部进程不得直接向通知表写数据。MCP Gateway、CLI、Worker、Box 和 Web BFF 只能调用 Core 的类型化业务契约；
- 首版不开放可填写任意标题、HTML 和任意用户列表的通用 `notifications.publish` 接口，避免绕过权限、模板审查、脱敏和防滥用规则。

### 通知类型与模板注册

每一种通知必须由所属业务模块在 Core 启动时注册稳定的 Notification Type，至少声明：

- `type_key` 和独立模板版本，例如 `project.invitation.received` + `template_version = 1`；
- 允许的来源事件及其 Schema Version；
- `system` 或 `project` 作用域，以及是否必须包含 `project_id`；
- 收件人解析器，例如指定用户、规范化邮箱、负责人、项目角色或项目成员集合；
- Inbox 策略：`required / default_on / optional / disabled`；
- 是否允许外部推送，以及允许进入外部模板的字段白名单；
- 标题、正文、严重级别、资源引用和类型化动作的渲染器；
- 对应生命周期事件及 `active / resolved / revoked / expired` 的单调转换规则。

注册表在 Core 启动时拒绝重复 Type、未知来源事件、无模板、无收件人解析器、允许输出密钥字段或缺少 Schema Version 的定义。模板由代码和契约版本控制，不允许业务事件直接携带可执行 HTML。

### 权威数据与状态

Notification：

- 保存 `notification_id`、Type、模板版本、来源事件、Project、Actor、关联资源、优先级、经过字段白名单过滤的模板数据、渲染快照和发生时间；
- 同一个来源事件可生成多个不同 Notification Type，但相同 `source_event_id + type_key` 只能生成一个 Notification。

Recipient：

- 保存 Notification 与目标用户或规范化邮箱之间的关系；
- 用户目标使用 `user:{user_id}`，注册前邮箱目标使用 `email:{normalized_email}` 作为稳定 `recipient_key`；
- `user.registered` 后将同邮箱且尚未过期的 Recipient 绑定到该用户；若用户目标已经存在，则事务内合并，不能产生两条收件项。

Inbox Item：

- 每个 Recipient 最多创建一个 Inbox Item；
- 阅读维度为 `unread / read`，归档由 `archived_at` 表达，业务结果维度为 `active / resolved / revoked / expired`；
- 用户标记已读或归档不能修改来源业务对象；来源业务完成也不能自动伪造用户已读；
- 支持 Cursor 分页，以及按 `project_id`、Type、阅读状态、归档状态、业务结果和发生时间筛选；
- 未读数只统计当前用户、未归档且 `read_state = unread` 的项目。

External Delivery：

- 每个 Notification、Project 渠道和目标组合生成一个稳定 Delivery；
- 状态机为 `pending → sending → delivered | retrying | failed | cancelled`；
- 每次尝试追加 Delivery Attempt，保存开始/结束时间、结果、安全错误码、HTTP 状态和响应摘要，不保存凭据或完整 Provider 响应；
- 成功 Delivery 不因 Outbox 重试、事件重放或 Core 重启再次发送；显式重新投递创建新的 `delivery_key`，不覆盖原记录。

### 内部收件箱产品能力

- Web 全局导航提供收件箱入口和未读角标，在 `/projects` 与 Project Workspace 中保持一致；
- 收件箱采用类似 GitHub Inbox 的 `未读 / 全部 / 已处理` 视图，首版提供项目、通知类型和时间筛选；
- 支持查看详情、标记已读、批量已读、归档和取消归档；首版不提供用户删除权威通知记录；
- Action 只包含浏览器安全的动作类型、资源 ID 和站内路由，不包含一次性 Token、Secret 或任意外部 URL；
- Security、邀请等 `required` 类型不可被 Project Rule 或用户偏好关闭；普通进度提醒未来可增加用户级订阅偏好；
- 平台级通知允许 `project_id = null`，Project 通知必须包含 Project 作用域并在查询时进行成员与收件人校验。

### 项目成员邀请闭环

邀请是首个完整接入 Inbox 的通知类型，流程必须覆盖已注册与未注册用户：

1. Project 在创建邀请的业务事务中写入 `project.member.invited`，载荷包含 `invitation_id / project_id / normalized_email / role`，不包含邀请明文 Token；
2. Notification 消费该事件，创建 `project.invitation.received`（模板版本 1）、邮箱 Recipient 和 Inbox Item；如果邮箱已属于现有用户，则同时绑定 `user_id`；
3. 已登录且邮箱匹配的用户通过 Inbox 使用 `invitation_id` 接受邀请，Core 增加受保护的 `POST /v1/projects/invitations/{invitationId}/accept`；Project 必须再次校验邮箱、有效期、撤销状态和一次性语义；
4. 未登录或未注册用户继续使用 3.16 的一次性 Token 链接完成预览、注册和接受，Notification 不负责保存或重建该 Token；
5. `user.registered` 将相同规范化邮箱下尚未绑定的有效 Inbox Item 认领到新用户；
6. 邀请接受时 `project.member.joined` 必须携带 `invitation_id`；撤销和过期分别发布 `project.invitation.revoked`、`project.invitation.expired`；
7. Notification 使用 `invitation_id` 将对应 Inbox Item 的业务结果更新为 `resolved / revoked / expired`，但保留原阅读状态和审计记录。

邀请消息默认只发送给被邀请人 Inbox，不得把被邀请邮箱广播到 Project 外部群渠道。未来 Email Adapter 如需发送 Token 链接，必须由 Project 提供专用的安全投递命令或短期动作句柄，不得把明文 Token 写入 Outbox。

### Project 级外部渠道

- 外部渠道以 `project_id` 为作用域，owner / maintainer 可以配置、启停、测试和删除，其他成员只能查看脱敏后的启用状态；
- 首版渠道为飞书群机器人 Webhook 和通用 Webhook；预留 Email、Slack、Teams 等 Adapter，不把 Provider 字段加入 Notification 通用模型；
- 渠道配置由 Notification 注册到 Settings。首版每个 Project、每种 Adapter 最多一个配置，使用稳定 key：`notification.feishu_webhook` 和 `notification.generic_webhook`；
- 飞书 Webhook URL 按 Secret 保存；通用 Webhook 的 Endpoint 不允许嵌入凭据，签名 Secret 按 Secret 保存；
- Settings 读取继续返回 `********`，只有 Core 内受信 Notification Adapter 可解析明文；连接测试必须返回安全检查项，禁止透传 Provider 响应正文；
- 删除或禁用渠道不删除历史 Delivery；尚未开始的 Delivery 转为 cancelled，已经发送的记录永久保留到统一留存策略清理。

### Project 通知规则

NotificationRule 使用已注册 Type，不允许规则创建未知类型或改变 Type 的收件人安全边界。

- Rule 至少包含 `project_id / type_key / external_enabled / channel_keys / minimum_priority / version`；
- Inbox 的 `required` 策略不可关闭，`default_on` 可以在未来由用户偏好覆盖；Project Rule 首版只控制外部渠道；
- Project 外部通知默认关闭，由 owner / maintainer 显式选择 Type 和渠道；
- 规则更新只影响更新后产生的 Notification，不追溯发送历史通知；
- 规则在生成 Delivery 时形成版本快照，后续配置变化不改变该 Delivery 的路由事实；
- Progress Reminder、任务逾期、实验失败、Article Release 等模块后续接入时，只注册 Type、模板和收件人解析器，不自建第二套通知渠道。

### 外部投递、幂等与重试

Event Bus 消费者只在数据库事务中创建 Notification、Recipient、Inbox Item 和 Delivery，不在消费事务中发起外部 HTTP 请求。Go Core 内运行 Notification Delivery Processor：

- 使用 `FOR UPDATE SKIP LOCKED` 领取到期 Delivery，并通过 `locked_by / lease_expires_at` 支持多 Core 实例和崩溃恢复；
- Adapter 调用有明确连接、请求和总超时，按指数退避加抖动重试，并支持每个 Project、每个渠道的基础限流；
- 通用 Webhook 发送 `X-Mmdash-Delivery-Id`、通知 Type、时间戳和 HMAC 签名，接收方按稳定 Delivery ID 去重；
- Provider 支持幂等键时传递 Delivery ID；Provider 不支持或网络超时结果不确定时按至少一次语义处理，不宣称严格恰好一次；
- 仅网络错误、429 和可恢复 5xx 自动重试；认证失败、签名配置错误和不可恢复 4xx 直接失败并生成安全诊断；
- 普通 Outbox Replay 只补齐缺失 Notification 或 Delivery，不重新发送 `delivered` 记录；管理员显式重投必须填写原因并写 Audit；
- 外部投递不使用 Python Worker Job Queue，避免把 Project 渠道明文凭据交给外部进程；短 HTTP 副作用由 Go Notification Adapter 和专用 Delivery Processor 完成。

### Core 与 BFF API

用户 Inbox：

- `GET /v1/inbox`：Cursor 分页与 Project、Type、阅读、归档、业务结果筛选；
- `GET /v1/inbox/unread-count`：返回全局未读数，并可选 `project_id`；
- `GET /v1/inbox/{inboxItemId}`：读取当前用户的一条收件项；
- `PATCH /v1/inbox/{inboxItemId}`：只允许修改 `read_state` 和归档状态；
- `POST /v1/inbox/mark-all-read`：按可选 Project/Type 范围批量已读。

Project Notification：

- `GET/PATCH /v1/projects/{projectId}/notification-channels/{channelKey}`：读取脱敏配置、启停和更新；
- `POST /v1/projects/{projectId}/notification-channels/{channelKey}/test`：连接测试；
- `GET/PUT /v1/projects/{projectId}/notification-rules/{typeKey}`：读取和更新规则；
- `GET /v1/projects/{projectId}/notification-deliveries`：查看投递状态和安全错误；
- `POST /v1/projects/{projectId}/notification-deliveries/{deliveryId}/retry`：显式重新投递。

BFF 在 `/api` 下提供一一对应的浏览器契约，使用 Session Cookie 调用 Core，不在 BFF 保存通知、规则、渠道凭据或未读状态。

### 权限、安全与隐私

- 用户只能读取和修改自己的 Inbox Item；知道 ID 不能读取其他用户消息；
- Project owner / maintainer 管理渠道、规则、连接测试和重新投递；editor / viewer 只能看到自身 Inbox，不读取渠道 Secret 或完整投递目标；
- Agent / Box Token 不能读取人类用户 Inbox，不能配置渠道，也不能调用通用通知发布接口；
- 通知模板只接收字段白名单，日志、Audit、Metrics、Outbox、Delivery Attempt 和 API 错误统一脱敏；
- 外部模板默认不包含邮箱、Token、Artifact Signed URL、原始日志或其他敏感内容；需要发送个人数据的 Type 必须单独设计并审查；
- 连接测试、规则变更、渠道变更、显式重投和通知 Action 写入 Audit；普通已读操作只保存状态，不产生高噪声领域事件。

### 纵向实现

- Web：全局收件箱入口、未读角标、未读/全部/已处理视图、筛选、详情、批量已读、归档，以及 Project 设置中的渠道、规则、测试和 Delivery 诊断；
- BFF：完整代理 Inbox 和 Project Notification API，保留 Cursor、ETag/Version 与稳定错误码；
- Core：`backend/internal/notification/`，实现 Type Registry、模板渲染、Recipient Resolver、Inbox Service、Rule Service、Event Consumer、Delivery Processor 和 Adapter Registry；
- Project：补齐按 `invitation_id` 接受邀请的登录态命令、邀请过期事件，以及接受事件中的 `invitation_id` 关联；
- Migration：`notification_notifications`、`notification_recipients`、`notification_inbox_items`、`notification_rules`、`notification_deliveries`、`notification_delivery_attempts`，包含唯一约束、Cursor/未读索引和 Delivery 领取索引；
- Settings：注册 `notification.feishu_webhook` 与 `notification.generic_webhook`，复用 Project RBAC、版本更新、加密、脱敏和连接测试；
- Events：首批消费 `project.member.invited`、`project.member.joined`、`project.invitation.revoked`、`project.invitation.expired` 和 `user.registered`；后续模块按 Type Registry 增量注册；
- Audit / Metrics：记录管理和敏感操作，暴露 Inbox 创建量、未读量、Delivery 延迟、成功、重试、失败和积压；
- Contracts：补齐 OpenAPI、事件 Schema、Type 模板 Schema、通用 Webhook Envelope 和 Adapter 契约；
- Tests：Store、Service、Registry、Resolver、模板白名单、状态机、幂等、邮箱认领、RBAC、Adapter、Processor、契约和 Web E2E。

### 验收

- 已注册用户收到 Project 邀请后可以在全局 Inbox 看到一条未读消息，通过受保护动作接受后加入 Project，Inbox Item 变为 resolved；
- 未注册邮箱先产生待认领 Inbox Item，用户以相同邮箱注册并接受邀请后只出现一条消息；不同邮箱不能查看或接受；
- 邀请撤销、接受和过期都通过 `invitation_id` 更新同一 Inbox Item，且不改变用户已经产生的阅读或归档行为；
- 同一事件重复消费、消费失败重试、Core 重启和普通 Replay 不产生重复 Notification、Recipient、Inbox Item 或 Delivery；
- owner / maintainer 可配置并测试飞书或通用 Webhook，启用 Rule 后新事件生成一个可追踪 Delivery，禁用 Rule 后不再生成新 Delivery；
- 外部渠道超时、429、5xx、认证错误和 Core 崩溃均按设计恢复或终止，不阻塞来源业务事务与内部 Inbox；
- 通用 Webhook 收到稳定 Delivery ID、时间戳和可验证签名；重试可能至少一次，但接收方能够可靠去重；
- 所有 Inbox、Project、Token 和渠道操作通过越权测试，API、日志、事件、Audit 和 Provider 错误中均不泄露 Secret 或邀请 Token。

# 4. 阶段 1：Repo 模块

Repo 是第一个 P0 功能模块，必须先完整纵向实现。

## 4.1 产品功能

- 一个项目默认绑定一个 Git Repo；
- `code / article / result` 三个逻辑工作区，分别映射到三个不同且已存在的远程分支；
- 已有 `main`、`master` 或其他分支都可映射为逻辑 `code`；
- 首版不自动创建、重命名、删除或强制覆盖远程分支；
- Worktree 同时访问三个分支；
- Git Provider 和本地仓库连接；
- 仓库状态；
- 分支、Commit、文件树和文件内容；
- Webhook 和 Commit 事件；
- 临时 Checkout；
- Core 内部受控文本写入、Commit 和普通 Push；Stage 1 Web 完全只读；
- article/result 分支提交；
- `ArticleWorkspace` 接口，为未来独立 article repo 保留扩展点。

## 4.2 纵向实现

- Web：设置页仓库连接、分支映射和状态；求解记录页只读浏览 Commit、文件树和内容；
- Web 不暴露文件编辑、Commit、Push，也不提前实现 Article 页面业务；
- BFF：Repo 页面、文件树、Commit 和内容接口；
- Core：Repo 领域模块和 Git 唯一入口；
- Adapter：GitHub、Local Git，后续可增加其他 Provider；
- Settings：Provider、URL、凭证、默认分支、三个业务分支；
- Data Hub：`repository`、`repo_commit`、代码文件对象；
- Events：`repo.connected`、`repo.commit.created`、`repo.commit.detected`；
- MCP：通过 `data.list/read` 提供仓库、Commit 和代码读取；
- Audit：连接、凭证测试、Checkout、编辑和提交；
- 测试：本地 Git、Webhook 幂等、Worktree、权限和 E2E。

## 4.3 验收

用户能在设置页绑定仓库，查看三个分支、Commit 和文件树；Commit 事件可靠进入 Outbox 和 Data Hub；后续 Agent、Experiment、Article 可通过稳定接口引用 Commit。

# 5. 阶段 2：Artifact 模块

Artifact 是第二个 P0 模块，为题目、附件、预览、实验结果和论文构建产物提供统一对象模型。

## 5.1 产品功能

- 题目原始文件和普通附件上传/下载；
- 文件元数据、Hash、MIME、大小、来源和状态；
- Signed URL；
- 图片、PDF、CSV、JSON、文本预览；
- 通用 Artifact 选择器；
- 图片、PDF、CSV、JSON、文本预览、缩略图和结构摘要；
- 附件注册表；
- 可空的人工描述、`recommended_usage` 字段和后续语义生成接口；
- 来源 Experiment、Model、Article 关联；
- Local、MinIO、S3；
- 小型结果包进入 Git，大型结果进入对象存储。

Stage 2 直接实现统一 multipart 上传：动态 part size、按需短期签名、有界并发、
单片重试、暂停/续传/刷新恢复/取消、Complete/Abort、过期会话清理，以及完成后的
完整大小和 SHA-256 校验。MinIO/S3 使用预签名 part PUT；Local 使用签名的
BFF/Core 流式传输路由，任何路由都不得缓冲完整 part 或文件。

对象存储 endpoint、bucket、凭据、上传限制、part size、Signed URL TTL 和清理周期
均为系统部署环境变量，不进入 Project Settings。Stage 2 提供 Project 内文件库，
不提供跨 Project 的账号级总文件库或系统存储管理面板。

## 5.2 纵向实现

- Web：文件抽屉、附件库、上传、详情、下载、预览和选择器；
- BFF：上传初始化、确认、下载和预览代理；
- Core：Artifact 领域模块；
- Worker：`artifact.preview`、缩略图、结构摘要和语义生成接口占位；
- Adapter：Local、MinIO、S3；
- Data Hub：`artifact`、`attachment_registry_entry`；
- Events：`artifact.created`、`artifact.available`、`artifact.deleted`；
- MCP：通过 `data.list/read` 提供元数据和受控下载；
- Audit：上传、下载、删除和 Signed URL；
- 测试：Hash 去重、状态机、预览失败、权限和 E2E。

Artifact 使用稳定逻辑 ID 和不可变 Version；分类为系统固定 `kind`、系统固定
`source` 与用户自由 `tags[]`，内容只在同一 Project 内按 SHA-256/大小去重。
普通删除进入可恢复回收站，成功文件及全部历史版本永久保留；只有用户在回收站
明确永久删除且 blob 无其他引用时才删除对象字节。自动清理仅处理未确认的过期
staging 上传和可再生成缓存。

Stage 2 不实现 Artifact CLI 命令、CLI 登录/项目选择、LLM/多模态语义描述或自动
`recommended_usage`。Stage 3 实现可扩展的 Go CLI 基座和本地 Coding Agent MCP
接入；Artifact 人工命令由 Artifact 后续迭代通过 CLI Feature 注册机制实现。真正
语义生成延后到 Article 阶段。

## 5.3 与 Project 接通

完成后将 Project 中的：

```
source_artifact_ids[]
```

接入题目卡片和项目创建流程，使用户可以上传题目、附件并在首页看到原始文件。

## 5.4 验收

任意模块都能通过稳定 Artifact ID 引用文件；用户可以上传题目和附件并预览；Data Hub 能统一列出和读取 Artifact；对象存储不泄露永久公开地址。

# 8. 阶段 5：Agent 会话

此阶段先实现人工使用的 Agent 会话，不立即加入自动进度跟踪。v0.1 的 Stage 5
只实现 `HermesAdapter`；`AgentAdapter` 是为后续 Runtime 保留的稳定扩展边界，
本阶段不实现第二种 Adapter。

## 8.1 Agent 域与 Adapter 边界

Agent 模块负责与具体 Runtime 无关的产品状态和工作流：

- 创建、切换、重命名、结束、继续和分叉 Session；
- `main / progress / experiment` 三类 Session；`main` 用于用户在 Web 中直接与 Agent 对话，`progress` 用于自动进度跟踪，`experiment` 用于实验结果分析，后续可按需增加类型；
- Session 索引、项目映射、名称、类型、状态和远端 Session ID；
- Agent 实例的 `manual / auto` 管理模式及其状态；
- 工具调用过程；
- 当前 Run 状态；
- 停止、重新生成和重新执行；
- 项目专用提示词自动生成、手工修改和恢复默认；
- Agent Token 的签发、待生效、激活、轮换和撤销工作流。

`AgentAdapter` 只定义 Runtime 无关的端口和规范化数据结构：能力探测、Session
生命周期、消息发送、事件流、Run、Job、项目访问配置、访问验证和统一错误。项目
访问端口只表达“配置或验证某个 MCP Endpoint 和凭证”，不得出现 Cloudflare、Hermes
Dashboard、Hermes API、SSE 事件名、Profile 或其他供应商字段。`AgentAdapter` 不保存
Agent 实例、管理模式、Project Grant、Token 状态或 Session 映射。每个具体 Adapter
必须通过能力探测分别声明是否支持项目访问验证、自动配置和自动轮换；不支持完整
自动生命周期的 Adapter 只能提供 `manual`，不得显示一个无法兑现的 `auto` 选项。

Stage 5 唯一的具体实现 `HermesAdapter` 负责：

- 使用 Hermes API Server 地址、API Key 和 Profile 调用 Hermes；
- 将统一 Session、消息、Run 和 Job 操作映射到 Hermes API；
- 把 Hermes SSE 事件、错误和能力信息转换为统一模型；
- 执行 Hermes 健康、鉴权、版本与能力检查；
- 在 `manual` 模式下只验证 Hermes 运行时连接和已由用户配置的 mmdash MCP，不修改 Hermes 配置；
- 在 `auto` 模式下通过 Hermes Dashboard 管理 API 安装、验证和更新 mmdash MCP，并处理管理地址可达性、Hermes Dashboard Session Token、可选的 Cloudflare Access 和 Gateway 重启；
- 将管理面的供应商专属结果转换为 `AgentAdapter` 的统一项目访问状态。

完整消息历史由 Hermes 保存；mmdash 的 Agent 模块保存 Session 索引和远端 ID
映射，`HermesAdapter` 本身不拥有该映射。

## 8.2 Hermes 配置与检查

Hermes Adapter 设置首先要求用户选择管理模式：

| 模式 | mmdash 的职责 | 用户的职责 |
| --- | --- | --- |
| `manual` | 签发和展示 Agent Token，记录配置状态，验证 Hermes 到 MCP Gateway 的实际访问 | 在 Hermes 中安装 mmdash MCP、保存 Agent Token，并在轮换时手工更新凭证 |
| `auto` | 通过可达的 Hermes Dashboard 管理面安装和更新 mmdash MCP、写入 Agent Token、执行验证并完成后续轮换 | 首次提供一个可从 HermesAdapter 运行环境访问且已授权的管理地址和管理凭证 |

两种模式的公共设置包括：

- Hermes API Server 地址；
- Hermes API Key；
- Profile / Agent 标识；
- 项目专用提示词；
- 默认 Session 策略。

`manual` 模式中的 Hermes Dashboard 地址可选。用户填写后，Agent 页面显示“打开
Hermes MCP 配置”入口；该入口只用于帮助用户完成或检查手工配置，不表示 mmdash
拥有 Hermes 管理权限。未填写时不显示入口，也不影响 Hermes 会话功能。

`auto` 模式还要求 Hermes Dashboard 管理地址和 Hermes Dashboard Session Token。
HermesAdapter 必须从自身运行环境探测管理地址，并按结果确定管理链路：

1. 管理 API 可以直连时使用 `direct`，不要求 Cloudflare 凭证。它适用于 mmdash 与
   Hermes 同机、同一可达内网或已有可信网络路径的部署。
2. 响应表现为 Cloudflare Access 挑战时使用 `cloudflare_access`，再要求 Access
   Service Token 的 Client ID 和 Client Secret，并通过 `Service Auth` policy 访问。
3. 地址不可达或认证类型不受支持时拒绝启用 `auto`，明确说明需要建立可达路径、
   补充凭证或改用 `manual`；不得静默降级。

管理链路可以根据探测结果自动建议，但最终结果必须显示在设置页并允许用户重新
探测。`localhost` 和私网地址均相对于 HermesAdapter 的运行环境解释：若 mmdash
运行在远端服务上，用户电脑上的本地 Hermes 不能因为填写 `127.0.0.1` 而被服务端
访问，必须改为同机部署、建立内网路径或使用 Tunnel。

管理地址属于受控 Connector 出站目标，不是通用 URL Fetch。实现时必须限制协议、
端口和重定向，重新校验每次 DNS 解析与跳转目标，拒绝 link-local、云元数据和其他
敏感地址；loopback 与私网访问仅在部署策略明确允许并通过 Hermes 管理 API 身份探测
后开放。所有探测和管理操作都需要超时、速率限制、脱敏日志和 Audit。

两种模式都要检查 Hermes API Server 的健康、鉴权、Session、Run、SSE、Jobs 和
版本能力。`manual` 额外验证已配置的 MCP 是否能访问 mmdash；`auto` 还必须检查
Dashboard 管理 API、配置写入、MCP 探测以及 reload/restart 能力。连接测试必须
区分运行时连接、管理面连接和 Hermes 到 MCP Gateway 的反向连接，不能用其中一个
成功代替另两个。

Hermes API Key 供 `HermesAdapter` 调用 Hermes；Hermes Dashboard Session Token 和
可选的 Cloudflare Access Service Token 供 `HermesAdapter` 管理 Hermes；mmdash
Agent Token 供 Hermes 调用 MCP Gateway。三类凭证方向和权限不同，必须分开加密
存储、脱敏展示、测试、轮换和撤销。`manual` 模式不保存 Hermes 管理凭证。

## 8.3 Agent 实例与 Agent Token

此阶段实现产品级 Agent 身份，而不是复用 Stage 3 的用户 CLI 凭证：

- Agent 模块创建和管理 Agent 实例、Adapter 类型、管理模式、Project Grant、状态和最后访问时间；
- Auth 为 Agent 实例签发高熵 opaque Agent Token，服务端只保存 SHA-256 Hash，明文只返回一次；
- Agent Token 绑定单个 Agent 实例、Project 和允许的 MCP Tool，不得继承创建者未明确授予的权限；
- `manual` 首次绑定时，mmdash 展示一次 Agent Token 和目标 MCP Gateway 信息，用户在 Hermes 中完成配置；验证成功前实例保持 `setup_pending`；
- `auto` 首次绑定时，Agent 模块签发待生效 Token，`HermesAdapter` 通过 Dashboard 管理 API 创建或更新 mmdash MCP、写入 Token 并验证，全部成功后才激活实例；
- MCP Gateway 验证 Agent Token、Project 和 Tool 权限，并将 Agent 身份传给 Core 再次执行领域鉴权和 Audit；
- Token 轮换必须允许新旧 Token 短时重叠。`manual` 模式向用户展示一次新 Token，待用户更新 Hermes 并验证后再撤销旧 Token；`auto` 模式由 `HermesAdapter` 写入新 Token、reload 或重启 Gateway、验证实际 MCP 调用后再撤销旧 Token；
- 自动轮换任一步骤失败时保留旧 Token 有效并回滚或标记 `rotation_failed`，不得先撤销旧 Token；
- 用户可随时立即撤销 Agent Token；撤销会阻断 Hermes 访问 mmdash，但 `manual` 模式下清理 Hermes 本地配置仍由用户负责；
- Stage 0 的静态 `MCP_AGENT_TOKEN` 只保留为本地开发和边界测试配置，不能用于产品绑定。

运行时链路固定为：

```
Hermes → MCP Gateway → Core → Project Data Hub
```

CLI 不参与 Agent Token 签发、保存或运行时转发。若未来提供 Agent 管理 CLI 命令，它也只是调用同一 Core 管理 API 的可选客户端，不是 Hermes 接入依赖。

## 8.4 Data Hub 与 MCP 接入

Agent 通过 MCP 读取：

- 项目题目和约束；
- Repo 和 Commit；
- Artifact；
- Progress；
- 后续 Model、Experiment、Article 对象。

接通 `context.promote`：Agent 可以提出显式项目上下文，但必须经过权限和结构校验；需要人工确认的内容进入 Context Proposal。

## 8.5 验收

用户可以在 mmdash 内连续与 Hermes Agent 对话、切换和分叉 Session、查看工具调用并停止/重跑；用户能选择 `manual` 完成最小手工接入，或选择 `auto` 由 mmdash 在管理地址可达且通过认证时完成 MCP 安装和安全轮换；`manual` 的可选 Dashboard 入口能够打开 Hermes 配置页；任一模式下 Hermes 都以可审计的独立 Agent 身份直接通过 MCP Gateway 读取获授权 Project 的真实数据，而不是依赖复制粘贴或用户设备上的 CLI。

- 用户 Commit 时可选择立即生成 LaTeX；
- 历史 Commit 可以单独触发 Build；
- 同一 Commit 可以有多次 Build；
- PDF 和 Build Report 登记为 Artifact；
- 失败 Build 不覆盖成功产物；
- Release 绑定指定 Commit 和一次成功 Build；
- Reference 固定来源对象 ID 和版本。

## 12.4 纵向实现

- Web：参考区、块编辑器、Patch、Tag、Build 和 Release；
- BFF：Article Workspace 聚合和流式状态；
- Core：Block、Patch、Tag、Reference、Commit、Build、Release；
- Repo：`ArticleWorkspace`、article branch 和 Commit；
- Artifact：图片、附件、PDF 和 Build Report；
- Worker：Markdown → LaTeX、模板、PDF Build 和报告；
- Adapter：Zotero；
- Settings：Zotero、LaTeX 模板和论文规范；
- Data Hub：`article_block`、`article_commit`、`article_build`、`article_release`；
- Events：Commit、Build、Release；
- Agent：Patch 和进度跟踪；
- Audit、引用一致性、构建和完整 E2E。

## 12.5 验收

用户能在左侧引用固定版本的题目、模型、实验和附件；编辑器支持 AI Patch 和审阅状态；任意 Markdown Commit 可生成 LaTeX/PDF；Release 明确绑定 Commit 与成功 Build；首页能展示论文完成度和最近 Release。

# 13. 阶段 10：完整闭环、加固与发布

## 13.1 产品闭环验收

```

  ↓

  ↓
创建关键节点与 TODO
  ↓

  ↓
Commit 或 Cron 触发自动进度跟踪
  ↓
从 Notion 同步模型形成 Snapshot
  ↓

  ↓
Box Gateway 调用 Sandbox Runtime 执行固定 Commit
  ↓
artifact.zip 归档并在求解面板展示、比较和分析
  ↓
Article 引用题目、模型、结果、附件和 Zotero
  ↓
Markdown Commit 生成 LaTeX/PDF
  ↓

```

# 14. 并行开发边界

完成技术基座和 P0 后，可以并行，但必须遵循数据和依赖边界。

## 14.1 可以并行

- Agent 会话与 Model，可在 Progress 基础稳定后部分并行；
- Model Worker 与 Model Web；
- Box Gateway 与 Experiment Web，在契约冻结后并行；
- Article 编辑器与 LaTeX Worker，在 Block/Build 契约冻结后并行；
- 各模块的 Data Hub 投影和 Web 页面。

## 14.2 不应提前并行

- Artifact 未稳定前，不提前为每个模块各自设计文件表；
- Repo 未稳定前，不在 Experiment 和 Article 中直接操作 Git；
- Progress 未稳定前，不让 Agent 直接创建自定义任务数据；
- CLI/MCP 最小闭环未完成前，不设计另一套 Coding Agent 接口；
- Experiment 契约未冻结前，不让 Box 接受临时私有请求格式；
- ArticleWorkspace 未稳定前，不绕过 Repo 写 article 分支。

# 15. 各阶段交付原则

每个阶段结束都必须交付：

- 可使用的用户流程；
- OpenAPI 和事件契约；
- Migration；
- Data Hub 投影；
- 权限和审计；
- 测试；
- 文档；
- 与已完成模块的集成。

禁止使用“先写完整后端，以后再补 Web”“先写临时表，以后再统一 Artifact”“先绕过 Core 直接写数据库”等方式制造第二套架构。
