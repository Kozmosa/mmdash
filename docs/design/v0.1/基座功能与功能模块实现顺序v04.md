> **范围原则：** 实现顺序只决定“由哪个模块负责、何时开发、依赖什么”，不得删除、降级或改写原设计中的首版功能。新增的合理架构设计继续保留。技术架构文档 v0.4：<page url="[https://app.notion.com/p/3aadf00a545d8184951eeea12291c1df"/](https://app.notion.com/p/3aadf00a545d8184951eeea12291c1df"/)>

# 1. 开发方式

采用“共同完成技术基座，之后按功能模块纵向开发”的方式。

```
全员共同完成技术基座
        ↓
依次完成 P0 前置功能模块
        ↓
由开发者纵向负责主要业务模块
        ↓
打通跨模块数据、事件和完整产品闭环
```

一个功能模块的完整纵向范围包括：

```
Web 页面与交互
→ Web BFF 路由
→ Core OpenAPI
→ Core 领域模块
→ 数据库 Migration
→ Settings 扩展
→ Adapter / Worker / Box Runtime
→ 领域事件与 Outbox
→ Data Hub 投影和 data.read
→ MCP Tool / CLI 支持
→ Audit
→ 单元测试、集成测试、契约测试、端到端测试
→ 模块文档
```

某模块确实不需要 Worker、MCP Tool 或外部 Adapter 时可以省略，但必须在模块文档中明确说明。不能只完成后端接口而不实现原设计中的页面、交互和完整用户流程。

```
阶段 0：技术基座

阶段 1：Repo
    ↓

阶段 3：clients/cli 与 MCP 产品层
    ↓
阶段 4：首页与 Progress
    ↓
阶段 5：Agent 会话
    ↓
阶段 6：自动进度跟踪
    ↓
阶段 7：Model
    ↓
阶段 8：Experiment + Box + Sandbox
    ↓
阶段 9：Article
    ↓

```

Repo、Artifact 和 CLI/MCP 是 **P0 前置功能模块**，不是技术基座。它们必须先纵向完成，因为后续模块都依赖项目版本、统一文件对象和外部 Agent 接入。

# 3. 阶段 0：技术基座

技术基座只提供所有功能共同依赖的机制，不实现 Git、附件、Agent、模型、实验、论文等具体领域能力。

## 3.16 登录、注册与成员邀请闭环

3.8 已提供 Session/JWT、登录接口与 bootstrap 账号，但技术基座只有内置管理员可登录，缺少自助注册与成员邀请，无法支撑多人协作。本阶段把 Auth 从“单个内置账号可登录”补齐为“可注册、可登录、可邀请、可管理”的完整身份闭环，为 Repo、Artifact 等 P0 模块提供真实的多用户与角色基础。成员与角色的权限语义沿用 3.8 RBAC。

### 账号与注册

- 自助注册：邮箱 + 密码注册，邮箱唯一（不区分大小写），注册即激活并可直接登录；
- 开放注册为系统级设置（`auth.allow_open_registration`），本地/单机默认开启，生产可关闭切换为纯邀请制；
- bootstrap 管理员仍由 `EnsureBootstrapUser` 保证存在，作为邀请制下的种子账号；
- 密码哈希、强度校验与错误信息脱敏复用 3.8 与 3.14 规范。

### 登录与会话闭环

- 登录、登出、`/auth/me` 已在 3.8 提供，本阶段补齐前端闭环：登录页、注册页、未登录路由守卫（中间件）与会话失效后跳回登录并回跳原页面；
- Web 经 BFF 下发会话 Cookie，受保护页面统一由守卫拦截，不再依赖逐页 401 兜底。

### 成员邀请闭环

- 邀请发起：owner / maintainer 可按邮箱邀请成员并指定角色（owner / maintainer / editor / viewer / agent / box）；
- 邀请载体：生成一次性、带过期时间的邀请 Token；已注册用户接受后直接加入，未注册用户凭邀请完成注册并加入；
- 接受与撤销：接受后建立成员关系并写入角色；发起方或管理员可撤销未接受的邀请；
- 成员管理：项目成员列表、角色变更与移除，全部经过 RBAC 校验；
- 幂等与并发：同一邮箱对同一项目的有效邀请幂等，Token 一次性使用、过期失效。

### 纵向实现

- Web：登录页、注册页、邀请接受页、路由守卫中间件、成员管理页（邀请、改角色、移除）、用户个人中心以及projects页完善；
- BFF：注册、邀请创建/接受/撤销、成员列表与角色管理路由，会话 Cookie 下发、用户个人信息控制；
- Core：Auth 增加注册与邀请用例；Project 增加成员/邀请领域操作与权限校验；
- Migration：`auth_invitation`（邮箱、项目、角色、Token 哈希、过期时间、状态），并按需扩展 `project_member`；
- Settings：`auth.allow_open_registration`、邀请 Token 有效期等系统级配置；
- Events：`user.registered`、`project.member.invited`、`project.member.joined`、`project.member.role_changed`、`project.member.removed`，与状态变更同事务写入 Outbox；
- Data Hub：投影 `user`、`project_member` 对象，接入 `data.list/read`；
- MCP / CLI：`project.member.*` 只读工具；CLI 登录沿用现有账号体系；
- Audit：注册、登录、邀请发起/接受/撤销、角色变更与移除全量审计；
- 测试：注册、登录、邀请、角色变更的单元、契约与 E2E，覆盖重复邀请幂等、Token 过期与越权邀请。

### 验收

- 开放注册开启时新用户可自助注册并登录；关闭后仅可凭邀请注册；
- owner / maintainer 邀请邮箱 → 被邀请人接受 → 以指定角色出现在成员列表并可访问项目；
- 未登录访问受保护页面被守卫重定向到登录页，登录后回跳原页面；
- 重复邀请幂等、撤销后不可接受、过期 Token 不可接受，全程可审计。

# 4. 阶段 1：Repo 模块

Repo 是第一个 P0 功能模块，必须先完整纵向实现。

## 4.1 产品功能

- 一个项目默认绑定一个 Git Repo；
- `code / article / result` 三个分支；
- Worktree 同时访问三个分支；
- Git Provider 和本地仓库连接；
- 仓库状态；
- 分支、Commit、文件树和文件内容；
- Webhook 和 Commit 事件；
- 临时 Checkout；
- 有限文本编辑；
- article/result 分支提交；
- `ArticleWorkspace` 接口，为未来独立 article repo 保留扩展点。

## 4.2 纵向实现

- Web：设置页仓库连接、分支配置、Commit 浏览；求解和论文共享文件树；
- BFF：Repo 页面、文件树、Commit 和内容接口；
- Core：Repo 领域模块和 Git 唯一入口；
- Adapter：GitHub、Local Git，后续可增加其他 Provider；
- Settings：Provider、URL、凭证、默认分支、三个业务分支；
- Data Hub：`repository`、`repo_commit`、代码文件对象；
- Events：`repo.connected`、`repo.commit.created`、`repo.commit.detected`；
- MCP：通过 `data.list/read` 提供仓库、Commit 和代码读取；
- Audit：连接、凭证测试、Checkout、编辑和提交；
- 测试：本地 Git、Webhook 幂等、Worktree、权限和 E2E。

## 4.3 验收

用户能在设置页绑定仓库，查看三个分支、Commit 和文件树；Commit 事件可靠进入 Outbox 和 Data Hub；后续 Agent、Experiment、Article 可通过稳定接口引用 Commit。

# 5. 阶段 2：Artifact 模块

Artifact 是第二个 P0 模块，为题目、附件、预览、实验结果和论文构建产物提供统一对象模型。

## 5.1 产品功能

- 题目原始文件和普通附件上传/下载；
- 文件元数据、Hash、MIME、大小、来源和状态；
- Signed URL；
- 图片、PDF、CSV、JSON、文本预览；
- 通用 Artifact 选择器；
- 附件自动描述；
- 附件注册表；
- `recommended_usage`；
- 来源 Experiment、Model、Article 关联；
- Local、MinIO、S3；
- 小型结果包进入 Git，大型结果进入对象存储。

## 5.2 纵向实现

- Web：文件抽屉、附件库、上传、详情、下载、预览和选择器；
- BFF：上传初始化、确认、下载和预览代理；
- Core：Artifact 领域模块；
- Worker：`artifact.preview`、缩略图、自动描述和 recommended_usage；
- Adapter：Local、MinIO、S3；
- Data Hub：`artifact`、`attachment_registry_entry`；
- Events：`artifact.created`、`artifact.available`、`artifact.deleted`；
- MCP：通过 `data.list/read` 提供元数据和受控下载；
- Audit：上传、下载、删除和 Signed URL；
- 测试：Hash 去重、状态机、预览失败、权限和 E2E。

## 5.3 与 Project 接通

完成后将 Project 中的：

```
source_artifact_ids[]
```

接入题目卡片和项目创建流程，使用户可以上传题目、附件并在首页看到原始文件。

## 5.4 验收

任意模块都能通过稳定 Artifact ID 引用文件；用户可以上传题目和附件并预览；Data Hub 能统一列出和读取 Artifact；对象存储不泄露永久公开地址。

# 7. 阶段 4：首页与 Progress

Progress 必须先于 Agent 自动跟踪完成，因为 Agent 的输出需要落到正式 Task、Milestone 和 Proposal 数据结构中。

## 7.1 首页功能

- 题目卡片和关键约束；
- 当前阶段和人工修正；
- 关键节点和延期状态；
- 今日、逾期、阻塞 TODO；
- 最新模型和变化；
- 实验状态和最新结果；
- 论文章节完成度、未审阅内容和最近 Release；
- Hermes 状态和最近进度更新时间；
- 摘要跳转到具体对象。

Model、Experiment、Article 尚未完成时，对应卡片使用标准 Empty State，不做临时假数据模型。

## 7.2 Progress 功能

- 人工关键节点；
- TODO、负责人、来源、关联对象和依赖；
- 看板；
- 列表；
- 日历/甘特；
- 今日视图；
- 提醒；
- 外部通知；
- Proposal 审阅。

## 7.3 规则

- 关键节点由人创建；
- Agent 未经确认不得修改关键节点；
- Agent 默认可创建和调整普通 TODO 及建议时间；
- 项目可配置普通 TODO 也只能生成 Proposal；
- 所有自动变更必须记录来源、Run 和审计。

## 7.4 纵向实现

- Web：首页、看板、列表、甘特、今日视图、提醒和 Proposal；
- BFF：Dashboard 和 Progress 页面聚合；
- Core：Milestone、Task、Dependency、Reminder、Proposal；
- Adapter：NotificationAdapter，首版保留飞书等外部通知扩展；
- Data Hub：`milestone`、`task`、`progress_proposal`；
- Events：Task、Milestone、Reminder、Proposal 全生命周期；
- MCP：`project.get`、`data.list/read` 的 Progress 内容；
- Audit 和完整 E2E。

## 7.5 验收

用户可以人工建立节点和任务，在看板、列表、甘特和今日视图中看到同一数据；提醒可触发；关键节点变更只能通过 Proposal 审阅；首页已有题目、节点和任务的真实聚合。

# 8. 阶段 5：Agent 会话

此阶段先实现人工使用的 Agent 会话，不立即加入自动进度跟踪。

## 8.1 Agent 会话功能

- Hermes 连接配置；
- AgentAdapter 与 HermesAdapter；
- 创建、切换、重命名、结束、继续和分叉 Session；

- SSE 流式回复；

- 当前 Run 状态；

- Hermes 管理面板入口；
- 项目专用提示词自动生成、手工修改和恢复默认。

完整消息历史由 Hermes 保存；mmdash 保存 Session 索引、项目映射、名称、类型和状态。

## 8.2 Hermes 配置与检查

设置至少包括：

- Hermes API Server 地址；
- API Key；
- Profile / Agent 标识；
- Hermes 管理面板地址；
- MCP Gateway 地址和 Agent Token；

连接测试必须检查：

- 健康状态；
- 鉴权；
- Session 创建和读取；
- Run；
- SSE；
- Jobs API；
- Hermes 到 mmdash MCP Gateway 的连通性。

## 8.3 Data Hub 与 MCP 接入

Agent 通过 MCP 读取：

- 项目题目和约束；
- Repo 和 Commit；
- Artifact；
- Progress；
- 后续 Model、Experiment、Article 对象。

接通 `context.promote`：Agent 可以提出显式项目上下文，但必须经过权限和结构校验；需要人工确认的内容进入 Context Proposal。

## 8.4 验收

用户可以在 mmdash 内连续与 Hermes Agent 对话、切换和分叉 Session、查看工具调用并停止/重跑；Agent 能通过 MCP 读取当前项目真实数据，而不是依赖复制粘贴。

# 9. 阶段 6：自动进度跟踪

自动进度跟踪是 Agent 的独立子阶段，不能遗漏，也不能仅实现一个 Cron。

## 9.1 触发方式

首版同时支持：

```
1. Cron：Hermes Jobs API
2. 领域事件：Commit、模型、实验、论文、任务等
3. 人工点击“重新评估进度”
```

重要触发事件至少包括：

```
repo.commit.created
model.snapshot.created
experiment.archived
article.build.completed
progress.task.updated
```

根据实际需要还可消费 Artifact、Release 和 Milestone 事件。

## 9.2 评估输入

- 题目；
- 项目约束；
- 关键节点；
- TODO；
- Repo Commit 和变化摘要；
- Artifact；
- Model Snapshot；
- Experiment 状态和归档结果；
- Article Commit、Build 和 Release；
- 显式项目上下文；
- 上一次评估结果。

## 9.3 评估输出

- 当前阶段；
- 总体摘要；
- 自上次以来的变化；
- 已完成项；
- 进行中项；
- 阻塞；
- 风险；
- 建议任务；
- 建议时间；
- 待确认问题；
- Proposal。

## 9.4 控制机制

必须实现：

- 项目级开关；
- Cron 配置；
- 防抖；
- 多事件合并；
- 最短评估间隔；
- 同一版本幂等；
- 失败重试；
- 评估历史；
- 最近评估时间；
- 手动重算；
- Agent 变更来源追踪；
- Proposal 审阅；
- 首页和 Progress 同步。

## 9.5 Progress 写入边界

- 普通 TODO：按项目设置自动创建/调整，或转为 Proposal；
- 关键节点：始终只能生成 Proposal；
- 当前阶段：Agent 可给出判断，用户可人工覆盖；
- 人工覆盖必须保留并影响后续评估；
- Agent 不得绕过 Progress 领域服务直接写表。

## 9.6 MCP Tool

接通：

```
progress.recalculate
```

并确保 `data.list/read` 可读取评估历史、阶段、风险和 Proposal。

## 9.7 验收

Repo Commit 或其他事件发生后，系统按防抖规则触发一次进度评估；首页阶段、摘要和 Progress 建议同步更新；关键节点不会被自动修改；用户可以查看完整评估来源和历史。

# 11. 阶段 8：Experiment、Box 与 Sandbox

Experiment 必须在 Repo、Artifact、CLI/MCP、Data Hub 和 Model 后实现。Box 是独立能力节点，但首版为 Experiment 提供 Sandbox Capability，因此在本阶段形成一个完整纵向切片。

## 11.1 先完成 Box 基础能力

### Core Box Control

- Box 注册和 Token；
- 心跳；
- 在线状态；
- 版本；
- Capability；
- Runtime；
- 负载和资源限制；
- 项目绑定；
- 调度和结果回传；
- 超时和失联处理。

### Box Gateway

- 注册与认证；
- 心跳和能力上报；
- 接收标准任务；
- 创建/销毁环境；
- 拉取固定 Commit；
- 注入只读输入和短期凭证；
- 日志、状态和结果流；
- 按 manifest 收集并回传 Artifact。

### Sandbox Capability

- 预定义镜像；
- 固定入口；
- 冻结参数；
- CPU、内存、时间和网络限制；
- stdout/stderr；
- 产物目录；
- 任务结束销毁。

Sandbox 不写代码、不改参数、不提交 Git、不保存长期 Workspace。

### Runtime

先实现：

```
SandboxRuntime
├── Local Docker
└── E2B
```

Local Docker 用于开发和联调；E2B 作为正式 Runtime Adapter，必须实现相同接口。

## 11.2 Experiment 产品功能

- Exp ID；
- 名称和状态；
- 创建者；
- source commit；
- entrypoint；
- 参数和环境；
- Box 和 Runtime；
- 日志；
- 失败原因；
- 资源消耗；
- 结果摘要和分析；
- 文件树和多格式预览；
- 多实验比较；
- 有限文本编辑；
- 外部 Coding Agent / Git / VS Code 入口；
- `artifact.zip`；
- 归档。

## 11.3 Experiment 状态和约束

- 一个 Exp ID 只允许成功启动一次；
- 创建后冻结参数、source commit 和 entrypoint；
- 不允许任意 Shell；
- 一个 Exp 对应零或一个主结果包；
- 失败保留日志但不产生成功结果指针；
- 归档前验证 manifest；
- 主结果包为 standalone `artifact.zip`。

```
artifact.zip
├── manifest.json
├── summary.md
├── logs/
├── figures/
├── tables/
├── data/
└── models/
```

## 11.4 MCP Tool

接通：

```
experiment.create
experiment.run
experiment.status
result.get
```

标准流程：

```
Coding Agent
  ↓ clients/cli stdio MCP
MCP Gateway
  ↓
Experiment Core 创建 Exp ID、冻结配置
  ↓
Box Control 选择 Box
  ↓
Box Gateway → Sandbox Capability → Runtime
  ↓
日志与状态回传
  ↓
manifest 验证
  ↓
Artifact / result branch 归档
  ↓
求解面板和 Data Hub 展示
```

## 11.5 纵向实现

- Web：实验列表、详情、日志、文件树、预览、比较、分析和 Box 面板；
- BFF：页面聚合、日志流、下载和比较；
- Core：Experiment 状态机和 Box Control；
- Box：Gateway、Sandbox、Local Docker、E2B；
- Repo：固定 source commit，必要时 result branch 提交；
- Artifact：主结果包、日志、图表和大文件；
- Worker：结果摘要、预览和比较预处理；
- Data Hub：`experiment`、`experiment_run`、`result_bundle`、`box`；
- Events：创建、开始、成功、失败、归档和 Box 事件；
- Agent：实验分析 Session 和进度跟踪；
- MCP：完整 Experiment Tool；
- Audit、契约测试、Runtime 测试和 E2E。

## 11.6 验收

Coding Agent 能通过 CLI/MCP 创建并运行实验；Box 只运行固定 Commit 和入口；日志实时展示；成功结果按 manifest 归档为 Artifact 或 result branch；失败保留日志；用户能比较多个实验并让 Agent 分析结果。

# 12. 阶段 9：Article 模块

Article 最后实现，因为它要引用题目、模型、实验结果、附件和 Repo，并完成 Markdown → LaTeX → PDF → Release 的最终闭环。

## 12.1 产品功能

- 左侧参考区：题目、Model Snapshot、Experiment Result、Artifact 和 Zotero；
- 右侧块级 Markdown 编辑器；
- 标题、段落、图片、表格、公式独立块；
- 稳定 `block_id`；
- 拖拽排序与组合；
- `/` 命令；
- AI Patch；
- 接受/拒绝 Patch；
- 行/块 Tag 和章节 Tag；
- Git 状态式颜色；
- 附件注册表；
- Zotero；
- Markdown Commit；
- LaTeX 生成；
- Build 历史；
- PDF；
- Release。

Tag：

```
章节：未编辑 / 未审阅 / 已审阅
块：AI 初稿 / 人工初稿 / AI 修订 / 人工修订 / 已审阅
```

## 12.2 Tag 推断规则

- 只出现于一个 Commit 且作者为 AI → AI 初稿；
- 只出现于一个 Commit 且作者为 Human → 人工初稿；
- 多个 Commit 中修改且最后作者为 AI → AI 修订；
- 多个 Commit 中修改且最后作者为 Human → 人工修订；
- 用户显式锁定 → 已审阅；
- UI 显示最近状态更新时间。

## 12.3 Commit、Build 与 Release

- Markdown 和生成的 LaTeX 进入 `article` 分支；
- 用户 Commit 时可选择立即生成 LaTeX；
- 历史 Commit 可以单独触发 Build；
- 同一 Commit 可以有多次 Build；
- PDF 和 Build Report 登记为 Artifact；
- 失败 Build 不覆盖成功产物；
- Release 绑定指定 Commit 和一次成功 Build；
- Reference 固定来源对象 ID 和版本。

## 12.4 纵向实现

- Web：参考区、块编辑器、Patch、Tag、Build 和 Release；
- BFF：Article Workspace 聚合和流式状态；
- Core：Block、Patch、Tag、Reference、Commit、Build、Release；
- Repo：`ArticleWorkspace`、article branch 和 Commit；
- Artifact：图片、附件、PDF 和 Build Report；
- Worker：Markdown → LaTeX、模板、PDF Build 和报告；
- Adapter：Zotero；
- Settings：Zotero、LaTeX 模板和论文规范；
- Data Hub：`article_block`、`article_commit`、`article_build`、`article_release`；
- Events：Commit、Build、Release；
- Agent：Patch 和进度跟踪；
- Audit、引用一致性、构建和完整 E2E。

## 12.5 验收

用户能在左侧引用固定版本的题目、模型、实验和附件；编辑器支持 AI Patch 和审阅状态；任意 Markdown Commit 可生成 LaTeX/PDF；Release 明确绑定 Commit 与成功 Build；首页能展示论文完成度和最近 Release。

# 14. 并行开发边界

完成技术基座和 P0 后，可以并行，但必须遵循数据和依赖边界。

## 14.1 可以并行

- Agent 会话与 Model，可在 Progress 基础稳定后部分并行；
- Model Worker 与 Model Web；
- Box Gateway 与 Experiment Web，在契约冻结后并行；
- Article 编辑器与 LaTeX Worker，在 Block/Build 契约冻结后并行；
- 各模块的 Data Hub 投影和 Web 页面。

## 14.2 不应提前并行

- Artifact 未稳定前，不提前为每个模块各自设计文件表；
- Repo 未稳定前，不在 Experiment 和 Article 中直接操作 Git；
- Progress 未稳定前，不让 Agent 直接创建自定义任务数据；
- CLI/MCP 最小闭环未完成前，不设计另一套 Coding Agent 接口；
- Experiment 契约未冻结前，不让 Box 接受临时私有请求格式；
- ArticleWorkspace 未稳定前，不绕过 Repo 写 article 分支。

# 15. 各阶段交付原则

每个阶段结束都必须交付：

- 可使用的用户流程；
- OpenAPI 和事件契约；
- Migration；
- Data Hub 投影；
- 权限和审计；
- 测试；
- 文档；
- 与已完成模块的集成。

禁止使用“先写完整后端，以后再补 Web”“先写临时表，以后再统一 Artifact”“先绕过 Core 直接写数据库”等方式制造第二套架构。
